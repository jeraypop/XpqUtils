### 重要发现：accessibility manifest 的 ShizukuProvider authority 被改成 .shizuku3
- 工作区有一处非本会话的改动：`rikka.shizuku.ShizukuProvider` 的 authority `${applicationId}.shizuku` → `.shizuku3`（应是用户为躲 manager 的 ShizukuManagerProvider authority 冲突而改）。
- 反编译官方 provider 13.1.5 确认：`ShizukuProvider.getBinder()` 硬编码 `Uri.parse("content://" + getPackageName() + ".shizuku")`，**不读 manifest**。
- 推论：`.shizuku3` 后，库取 binder 落到 manager 的 ShizukuManagerProvider（占 pkg.shizuku）——方案成立与否取决于该 provider 是否实现了 METHOD_GET_BINDER/BinderContainer 转发；否则 pingBinder 失败、UiAutomation 通道断。
- 回退方案（真机验证失败时用）：authority 改回 `.shizuku` + app manifest `tools:node="remove"` 掉 `moe.shizuku.manager.ShizukuManagerProvider`。

### 修复：:AccessibilityService 子进程 UninitializedPropertyAccessException 崩溃
- 现象：`com.smdemo.msg:AccessibilityService` 进程启动即崩，`lateinit property appContext has not been initialized`，栈在 App.onCreate:54 → NotificationUtilXpq.toggleNotificationListenerService 默认参数取 LibCtxProvider.appContext。
- 根因：无障碍服务在库 manifest 声明 `android:process=":AccessibilityService"`（第 163 行）；ContentProvider（LibCtxProvider）默认只在主进程实例化，子进程里 onCreate 不执行、appContext 未赋值；而宿主 Application.onCreate 每个进程都会跑 → 必崩。
- 修复：`LibCtxProvider` companion 新增 `manualInit(context)`（幂等，`::appContext.isInitialized` 守卫；最小初始化 appContext/contentProviderAuthority/SPUtils/版本信息，配 static 版 tryGetAppBuildTime/getAppName）；`App.onCreate` 最前面 `runCatching { LibCtxProvider.manualInit(this) }`。
- 注意：子进程仍未执行的 provider 逻辑（KeyguardUnLock 唤醒、OtpCenter 验证码收集、RuntimeTracker）——若子进程业务需要，再按需补进 manualInit。
- 验证：`:accessibility` + `:app` → **BUILD SUCCESSFUL**。
