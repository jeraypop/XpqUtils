## 更正：昨天对「clearFocusedText 合并 exec」收益的估算偏高（01:48）
起因：用户问「没加固的时候是不是跟之前一样」。为此回读 `AutomationUserService.exec()` 才确认既有事实：

- **`AutomationUserService.exec()` 的实现是 `ProcessBuilder("sh","-c",command).start()`（第 58 行）**，
  即**每次 `exec()` 调用都会 fork 一个 sh 进程**，无论走 UserService 还是 newProcess。

据此重新核算 10-06 的 ② 改动（`repeat(120){exec("input keyevent 67")}` → 合并成一条 sh 脚本）：

| | binder 往返 | sh 进程 | `input` 进程 |
|---|---|---|---|
| 改前（120 次 exec） | 120 | 120 | 120 |
| 改后（1 次 exec + sh 内循环） | 1 | 1 | **120（未减少）** |

- 真正的大头是 **120 次 `input` 进程启动**（`input` 是 ART 程序，单次约 50~150ms，合计 6~18 秒），
  它**在 sh 循环里依然存在**。省下的只是 119 次 binder 往返 + 119 个 sh（toybox sh 很轻，约 3~8ms），
  合计约 0.5~1s（newProcess 路径因每次新进程创建更贵，约 2~3s）。
- 故 10-06 记录的「12~36 秒 → 单次 shell 往返」是**错的**：把「exec 调用次数」当成了「进程启动次数」。
  实际加速幅度有限，加固与否都如此。
- 教训：估算 shell 耗时前，必须先确认 exec 的**真实实现层级**（UserService 内部是不是 ProcessBuilder）。

## 核实到的可用事实（已验证用法字符串）
- `input keyevent` 官方 usage（来自 `frameworks/base/.../InputShellCommand.java`）：
  `keyevent [--longpress|--doubletap] <key code number or name> ...` —— `...` 表示**一次可传多个 keycode**，
  例：`input keyevent 26 107`。
- 因此 API<30 的清空可以写成 `input keyevent 123 67 67 ... 67`（120 个 67）→ **1 个进程、1 次 exec**，
  这才是真正消掉 120 次进程启动的写法。
- 待真机验证：多 keycode 之间的间隔问题。AOSP 里 `input` 的 key 注入用
  `INJECT_INPUT_EVENT_MODE_WAIT_FOR_FINISH`（等本次分发结束再发下一个），据此推断连发不会丢键，
  但**未经实测，不能直接替换**。

## 三处改动在「未加固」场景下的实际影响（回答用户）
- ① 超时 15s→3s：正常设备绑定 1s 内完成，走不到超时 → **行为一样**。唯一差异是绑定耗时落在
  3~15s 的慢机型会被判 `userServiceUnavailable` → 该进程内永久降级（shell 每次 fork、tap 回退
  input swipe），功能仍可用只是变慢。想要余量就把 3s 调到 5s，代价是加固机日志多静默 2 秒。
- ② 见上：未加固时也**只有约 1 秒级收益**，远小于当初的说法。
- ③ 删掉 `SystemClock.sleep(1000L)`：未加固时**同样生效**，每次滑动手势快 1 秒（刻意改的）。
