4. 更新 `MusicConstants.kt` 注释（原「ExoPlayer 可直接流式播放」已过时）。

验证：`:accessibility:assembleDebug` → **BUILD SUCCESSFUL**。

## 修复：播放列表卡片「播放按钮」暂停后不能继续播放（本轮）

用户实测：点列表里某首歌的卡片播放按钮，暂停后再点，无法「继续播放」。
根因：`MusicActivity.togglePlayAt(pos)` 原来只用 `playingThis = (state==PLAYING && index==pos)` 判断——暂停态下该条件为 false，于是走到 else 分支调用 `MusicManager.play(pos)`；而 `play()` 内部会 `prepareAndPlay → player.reset()` 从头重新准备，导致暂停的同歌被「从头重播」而非从暂停处恢复（表现即「点了不能继续」）。主控制栏的 `togglePlay()` 本来就有 `PAUSED -> resume()`，只是卡片按钮漏了这分支。

## 修复：暂停后再点播放（续播）没声音（彻底方案，本轮已验证 BUILD SUCCESSFUL）

用户反复实测：点某首播放 → 点同一首暂停 → 再点「播放」→ 不出声。前几轮打补丁（holdPaused 等）都没解决。
**真正根因**：续播一直走「复用同一个 MediaPlayer 实例 + `player.start()` 续播」思路，而 MediaPlayer 在部分机型/音频格式（FLAC、本地 content://）上「pause 后 start」会**静默失败**（无异常也不出声）。第一首能播是因为它走的是全新实例的 `prepareAndPlay()`，续播却没走这条路径。
**彻底修复（改 MusicManager.kt）**：不再复用实例续播，改为「暂停即彻底释放、续播即重建并 seek」。
- `pause()`：记录 `pausedPosition = player.currentPosition`，`player.pause()`，然后 `releasePlayerInternal()`（彻底释放，不再持有旧实例）。
- `resume()`：直接 `prepareAndPlay(currentSong, seekToMs = pausedPosition)`——重建干净实例并从暂停位置 seek 续播。
- `prepareAndPlay(song, seekToMs=0)`：新增 `seekToMs` 参数；准备时置 `pendingSeek`/`preparing`，`preparedListener` 在 `onPrepared` 里先 `seekTo(pendingSeek)` 再 `start()`。
- 删除脆弱的 `holdPaused` 机制，改用 `preparing`/`pendingSeek`/`pausedPosition` 三字段。
- `stop()` 一并重置这三个字段。
**关键洞察**：既然「第一首能播」靠的是 `prepareAndPlay`（每次都全新实例），让续播也走同一条已验证路径，就保证续播和首播一样可靠。
验证：`:accessibility:assembleDebug` → **BUILD SUCCESSFUL**。
经验教训：**MediaPlayer 的「暂停后继续」不要依赖复用同一实例的 `start()`，尤其 FLAC / content:// 本地文件；最稳的是「pause 时释放、resume 时重建+seek」。** 之前多轮无效是因为没换模型，只在复用模型上打补丁。

## 真正根因 + 修复：音频焦点请求每次新建导致死循环（logcat 定位，本轮）

用户给了 logcat，发现续播时反复：
`prepareAndPlay idx=2 ...FLAC scheme=file seek=3456` → `onAudioFocusChange(-1)`(AUDIOFOCUS_LOSS) → 又 `prepareAndPlay` …
**根因**：`requestAudioFocus()` 每次 `prepareAndPlay` 都 **新建一个 AudioFocusRequest** 并重新请求。Android 用新请求「取代」旧请求时，被取代的旧请求会立刻收到 `onAudioFocusChange(-1)`(LOSS) → 回调里调 `pause()` → 旧 pause 会 `releasePlayerInternal()` 把**正在 prepare 的播放器销毁** → 永远不出声、且每点多一次就重复一轮。第一首能播是因为那时还没反复重建焦点请求。
**修复（三处）**：
1. `requestAudioFocus()` 改为**复用单一 `focusRequest` 实例**（只在 `== null` 时创建一次），不每次新建，从根本上消除「取代旧请求触发 LOSS」；焦点监听器提取为字段 `focusChangeListener` 复用。
2. 焦点丢失（`LOSS`/`LOSS_TRANSIENT`）回调改调 **`internalPause()`**（只挂起播放、不释放正在 prepare 的 player、不放弃焦点），不再调会销毁 player 的 `pause()`；`preparedListener` 增加 `wantPauseWhenReady`：若 prepare 期间被要求暂停，准备好后保持 PAUSED 不出声，避免破坏 prepare。
3. `pause()`（用户主动）拆为 `internalPause()` + `abandonAudioFocus()`：用户主动暂停才释放焦点，避免长期霸占；`internalPause` 在 `preparing` 期间设 `wantPauseWhenReady` 而非直接动 player。

## 优化：批量缓存限制并发数（本轮，避免歌多时同时下载过多）

用户提醒：在线曲库歌曲很多时，原 `MusicCache.cacheAll` 每首歌各起一个 `CoroutineScope(Dispatchers.IO).launch`，**无限并发**会一次性拉起几十个连接，既费带宽又易因系统/机型并发限制大量失败。
改动（`MusicCache.kt`）：用 `java.util.concurrent.Semaphore(MAX_CONCURRENT_DOWNLOADS=3)` 限制同时下载数；`cacheAll` 里每首 `launch` 后先 `semaphore.acquire()`（在 IO 线程阻塞排队，不空转），`try{ download } finally{ release() }`，完成一个再放下一个。
坑：`kotlinx.coroutines.sync.Semaphore.withPermit` 在当前 coroutines 版本里解析不到（回退成 java.util.concurrent.Semaphore 后无 withPermit 报 unresolved），故改用 JDK `java.util.concurrent.Semaphore` 的 `acquire()/release()`，跨版本稳定。

## 修复：TTS 首次点击试播不播报（本轮）
用户反馈 TTS 试播按钮第一次点击不播报、第二次才播。根因：`TTSManager.speak`（baoshi/TTSManager.kt）中 `TextToSpeech(..., this)` 是异步构造，`onInit` 回调后才置 `ready=true`；原逻辑在 `ready` 为 false 时直接丢弃本次文字，导致首次点击的文字丢给引擎、无补播，第二次点击因引擎已就绪才播。
改动（仅 TTSManager.kt）：
- 新增 `pendingText` 字段；`speak` 在 `ready=false` 时把文字暂存到 `pendingText`（连续点击只留最后一次）。
- `onInit` 成功（`status==SUCCESS`）后，若 `pendingText` 非空则立即补播并清空。
- `stop()` 同步清空 `pendingText`，避免停止后残留补播。
效果：首次点击也能在引擎就绪后立刻播报。验证 `BUILD SUCCESSFUL`。

## 修复：子线程调用 playSaved() 悬浮窗崩溃（本轮）
用户问"子线程调用 playSaved() 还能正常工作吗"。诊断：`playSaved()`(MusicPlayer.kt, 无 context 参数, 用 appContext) 路径中——①读开关 ②restoreAndPlay(prepareAsync+主线程 Handler) ③TTS ④悬浮窗 show。前三项子线程安全；唯独 ④`MusicControlFloatWindow.show()` 的 `windowManager.addView`（行100）必须在主线程，子线程无 Looper 会抛 "Can't create handler..."，且 catch 内 `AliveUtils.toast` 子线程二次崩溃，导致悬浮窗不显示且可能把调用方线程带崩。
修复（仅 MusicControlFloatWindow.kt）：`show()` 开头判断 `Looper.myLooper() != Looper.getMainLooper()`，则 `Handler(Looper.getMainLooper()).post { show(...) }` 后 return，自动切主线程执行 inflate/addView/toast；加 import android.os.Handler/Looper。主线程调用路径不受影响。验证 `BUILD SUCCESSFUL`。

## 加固：listener 回调统一切主线程（本轮，应"再加一道保护"）
上一轮指出：若 MusicActivity 注册了 listener，子线程 playSaved 时 `restoreAndPlay` 经 `listeners.forEach` 通知 UI 可能在子线程触发崩溃。
改动（仅 MusicManager.kt）：
- 新增私有 `notifyListeners(action: MusicListener.() -> Unit)`：先 `synchronized(listeners){ toList() }` 拷贝快照（防并发 CME），再 `handler.post { 遍历 snapshot 执行 action }`，保证所有 listener 回调都在主线程。
- 将 9 处 `listeners.forEach { it.onXxx(...) }`（error/state/playlist/IDLE/play 内等）替换为 `notifyListeners { onXxx(...) }`；`addListener` 的初始化同步回调也改为 `handler.post { l.onMusicState/onMusicPlaylist }`。

效果：无论播放逻辑在哪个线程触发，所有 UI 监听回调都在主线程执行，子线程调用 playSaved 彻底安全。验证 `BUILD SUCCESSFUL`。

## 修复：删除列表歌曲却触发震动/TTS（本轮）
Bug：在 MusicActivity 列表删除**正在播放**的歌时，`MusicManager.removeAt` 原 `play(newIdx)`（play 默认 accompany=true）会带起震动/TTS；删到列表空时走 `stop()` → `syncVibrateFromSettings()` 也可能新起震动。违反"列表操作只管歌曲"原则。
改动（仅 MusicManager.kt）：
- `removeAt(index, accompany: Boolean = false)`：续播分支改 `play(newIdx, accompany)`；删到空分支改 `stop(stopVibrate = accompany)`。
- `stop(stopVibrate: Boolean = true)` 新增参数：默认 true（按设置同步震动，原有外部/焦点丢失等行为不变）；列表删除传 false 时**不改动震动状态**（既不新起也不停）。
- **踩坑**：上一版把删到空分支误写成 `stop(stopVibrate = !accompany)`，`!false=true` 导致列表删除仍走震动同步、单首歌删除仍会新起震动。正确应为 `stop(stopVibrate = accompany)`（accompany=false → false → 不改动震动）。已修正验证 `BUILD SUCCESSFUL`。
- `reorder` 仅调 loadPlaylist，无 play/stop，天然不涉及震动/TTS，未改。
- `deleteAt` 调 `removeAt(pos)`（默认 accompany=false），无需改。
效果：列表内删除任意歌曲（含正在播放的、删到空的）都只管理歌单，绝不触发/改动震动与语音。验证 `BUILD SUCCESSFUL`。

## 悬浮窗水平居中修复（真机未居中 bug）
- 根因：原 `gravity = TOP | START` + addView 前 `measure(UNSPECIFIED)` 手动量宽算 `x=(screenW-viewW)/2`；实测渲染宽度 ≠ 预测量宽度，导致 x 偏大、整体偏右、看起来没居中。
- 修复：改用 `gravity = Gravity.TOP or Gravity.CENTER_HORIZONTAL` + `x = 0`（让 WindowManager 自行水平居中，x 语义变为「相对屏幕水平中心偏移」），删除手动 measure 代码块与 `MeasureSpec` import。
- 配套：拖动监听器 `DragTouchListener` 的水平夹紧范围从 `coerceIn(0, screenW-v.width)` 改为对称 `coerceIn(-(screenW-v.width)/2, (screenW-v.width)/2)`（贴左/贴右）；垂直 clamp 不变。验证 `BUILD SUCCESSFUL`。
