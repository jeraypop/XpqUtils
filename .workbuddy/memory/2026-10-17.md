## 趣安卓 8.0.47 崩溃：BadTokenException（03:50 定位并修复）
用户报「Shizuku 权限弹窗现在能点了，但报了错」，崩溃栈：

```
android.view.WindowManager$BadTokenException: Unable to add window -- token android.os.BinderProxy@d344bd3
  is not valid; is your activity running?
  at android.view.ViewRootImpl.setView(ViewRootImpl.java:1765)
  at android.app.Dialog.show(Dialog.java:352)
  at XpqAcc.showUiAutomationFailDialog(SourceFile:124)
  ... showEngineModeDialog$lambda$17$applyModeAndGuideToSetting$2
  ... connectUiAutomation$lambda$3$0
  at android.os.Handler.handleCallback(Handler.java:959)
```

**根因**：`XpqAcc.showUiAutomationFailDialog(activity, reason)` 是**异步**回调 —— 连接尝试彻底结束后才走到这里，
中间的等待期里宿主传进来的 `activity` 可能已经 `finish` / 重建，此时 `AlertDialog.Builder(activity).create().show()`
拿到的窗口 token 已失效。而 `dialog.show()` 外面**没有 try/catch**，异常直接抛到主线程回调里 → 崩整个应用。
（`connectUiAutomation` 里 `main.post { ... }` 的那条失败链同理。）

**与 Shizuku 权限弹窗那次修复的关系**：无关，是**两个独立问题**。但这次崩溃**只在权限弹窗能点之后才暴露出来** ——
以前点不动 → 拿不到授权 → 走的失败路径不同。现在能点了 → 走到这条失败分支 → 崩。

**排查过程中的旁证**（本机联想 TB320FC / Android 15）：
- `settings get global always_finish_activities` = `null` ⇒ **不是**"不保留活动"开发者选项导致的销毁；
- `dumpsys dropbox --print data_app_crash` 无记录（崩溃由宿主自己的 `XpqUncaughtExceptionHandler` 捕获上报，没进 dropbox）。
- ⇒ 具体是什么把 Activity 销毁的还没定死，但**不依赖它**：只要"捕获 Activity 后延迟使用"就必须做存活检查。

**修法**（`XpqAcc.kt`，1 文件）：
```kotlin
if (activity.isFinishing || activity.isDestroyed) {
    AliveUtils.toast(msg = "Shizuku 模式 连接失败：$msg")
    return
}
...
if (runCatching { dialog.show() }.isFailure) {   // 检查与 show 之间仍有同帧竞态
    AliveUtils.toast(msg = "Shizuku 模式 连接失败：$msg")
    return
}
```
降级成 toast 而不是硬弹窗：**宁可不弹，也不能崩**。代价是 Activity 已死时丢掉「打开 Shizuku」按钮（可接受，
重开 App 即可重试）。

**验证**：`./gradlew :accessibility:compileDebugKotlin --offline` → **BUILD SUCCESSFUL in 34s**。**未提交。**

**副产物**：崩溃把真实失败原因挡住了 —— 修完后 toast/弹窗会显示 reason，这也是判断"连接为什么失败"的依据。

## 调研：悬浮窗权限能否代码开启（15:00，**未改代码**，用户要求先不动手）
- `SYSTEM_ALERT_WINDOW` 是 **appops 特殊权限**，不是运行时权限。`Settings.canDrawOverlays()`
  （`Settings.java:4029`）= `isCallingPackageAllowedToDrawOverlays` → `AppOpsManager.OP_SYSTEM_ALERT_WINDOW`
  的 `noteOpNoThrow`/`checkOpNoThrow`：`MODE_ALLOWED` → true；`MODE_DEFAULT` → 再查
  `SYSTEM_APPLICATION_OVERLAY`（signature 级）静态权限。
- ⇒ **`pm grant` 无效**（非 dangerous，走不到运行时权限通道）；`Settings.Secure` 里**没有**这个键 ⇒
  `WRITE_SECURE_SETTINGS` 帮不上；**无障碍服务 / UiAutomation 也没有** `MANAGE_APP_OPS_MODES`，不能代开。
- **唯一能「代码开启」的路 = shell（uid 2000）**：`appops set <pkg> SYSTEM_ALERT_WINDOW allow`。
  已核实：AOSP `packages/Shell/AndroidManifest.xml`（android-14.0.0_r1）确实声明
  `<uses-permission android:name="android.permission.MANAGE_APP_OPS_MODES" />`；
  `AppOpsService.setMode` 只走 `enforceManageAppOpsModes`（系统进程 / profile owner / 该权限），
  **没有针对 OP_SYSTEM_ALERT_WINDOW 或 restricted op 的特殊拦截**，也**不要求**调用者与目标包同 uid。
- 本库现成通道：`XpqAcc.execShell(cmd)` → `AccessibilityEnableHelper.execShell` →
  `InvisibleAutomation.exec`（UserService 优先、`execViaNewProcess` 兜底）。**阻塞**，必须后台线程
  （遵守「库内阻塞型能力的对外形态」那节：同步版 + `xxxAsync`）。
- 回读**不要**再 fork 一次 `appops get`（每次都是新起一个 `app_process`/ART 进程，成本几百 ms）：
  进程内 `Settings.canDrawOverlays()` 或 `AppOpsManager.checkOpNoThrow(OP_SYSTEM_ALERT_WINDOW, uid, pkg)`
  即可；后者还能区分「没设过 `MODE_DEFAULT`」与「用户明确拒绝 `MODE_IGNORED`」。
- 授权**实时生效**，不需要重启进程（`canDrawOverlays` 每次都现场查 appops）。
- 无 Shizuku 时兜底：`Settings.ACTION_MANAGE_OVERLAY_PERMISSION` + `Uri.parse("package:$pkg")`
  （部分 ROM 会忽略 package 参数，落到列表页）。
- ⚠ 国产 ROM（MIUI/HyperOS/EMUI/ColorOS）可能另有一套权限管理，appops 设成 allow 后悬浮窗仍可能被拦
  → **必须实机验证**，不能只看 `canDrawOverlays` 的返回值。
- 结论：可以做，但**只在 Shizuku 通道可用时**是"全自动"；纯无障碍模式仍需跳设置引导。

## 落地：连接成功后自动开启悬浮窗权限（15:10，已验证编译）
- 新增 `ext/utils/safecheck/OverlayPermissionHelper.kt`（object）：
  - `canDrawOverlays(ctx)` = `Settings.canDrawOverlays`，纯进程内、**零成本**；
  - `OverlayResult(success, viaShell, message)` —— `EnableResult` 的悬浮窗版，但**没有 WRITE_SECURE 分支**
    （S.A.W 是 appops、`Settings.Secure` 里没这个键），`viaShell` 语义改述为「本次是否真的执行了 shell」；
  - `enableOverlayPermission(ctx)`：已授权**短路不 fork** → `appops set <pkg> SYSTEM_ALERT_WINDOW allow`
    → 用 `Settings.canDrawOverlays` **进程内**回读（刻意不再 fork 一次 `appops get`）。
    失败分三种成因写进 message：shell 不可用 / `exitCode != 0`（带 stderr）/ 回读仍不放行（疑似厂商拦截）。
- `XpqAcc` 新增门面 `canDrawOverlays` / `enableOverlayPermission`（`@JvmStatic @JvmOverloads`），
  放在 `execShell` 之后、「无障碍服务直接开启」之前。
- `connectUiAutomation` 的 `finishConnect`：插在 **`DynamicIslandFloatWindow.autoInit()` 之前**，顺序是**必需的** ——
  `autoInit()` 内部 `handler.post` 切主线程（本次调用异步返回），只有当前线程先同步跑完 appops，
  才能保证它真正落地时权限已就绪。失败只 `log()`，**不改变连接成功结果**。
- API 选择的两个坑：`OP_SYSTEM_ALERT_WINDOW`（int）是 `@hide`、`checkOpNoThrow(String,int,String)` 是
  `@FlaggedApi`（新 API，老设备可能不可用）→ 两者都**不碰**，只用公开的 `Settings.canDrawOverlays`。
  `appops` 命令的 op 名用 `SYSTEM_ALERT_WINDOW`（不是 `android:system_alert_window`，后者是 `OPSTR_*` 常量）。
- 验证：`./gradlew --offline :accessibility:compileDebugKotlin :app:compileDebugKotlin`
  → **BUILD SUCCESSFUL in 27s**，0 error / 0 warning。**未实机验证**（appops 在国产 ROM 上必须实测）。
