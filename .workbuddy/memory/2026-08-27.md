# 2026-08-27 — XpqUtils accessibility 库双通道（无障碍 / UiAutomation）无缝切换

## 关键结论 / 限制
- `getRootInActiveWindow/getWindows/findFocus` 是 AccessibilityService 非 final 方法，可被 ProxyAccessibilityService 覆盖 → 库里几十处 `rootInActiveWindow` 调用零改动自动路由。
- `performGlobalAction/dispatchGesture` 是 final，只能改库内封装点（仅 3 处，很集中）。
- **事件驱动（asyncHandle_XXX）在 UiAutomation 模式下无法「零改动」等价**：宿主的事件处理器是 SelectToSpeakServiceAbstract 的实例方法，UiAutomation 模式没有 service 实例。事件桥接接口已通过 `AccDriver.setOnAccessibilityEventListener` 提供，宿主可 `XpqAcc.setOnAccessibilityEventListener { event -> ... }` 主动监听（属新增可选能力，非改动现有代码）。

## 宿主使用方式（零改动）
```kotlin
// App 启动时一次性配置（切换通道），业务代码完全不动
XpqAcc.use(EngineMode.UIAUTOMATION)   // 切 UiAutomation（免开无障碍，需 Shizuku）

// Shizuku 前置检测/授权（UiAutomation 通道必需）
if (!XpqAcc.isShizukuRunning()) { /* 提示用户先启动 Shizuku */ return }
if (!XpqAcc.isShizukuPermissionGranted()) {
    XpqAcc.requestShizukuPermission { granted ->
        if (granted) XpqAcc.connect { log -> ... }
    }
    return
}
XpqAcc.connect { log -> ... }          // 连接

// 或
XpqAcc.use(EngineMode.ACCESSIBILITY_SERVICE)  // 切回无障碍（默认）
```
业务代码照旧：`accessibilityService?.clickByText("设置")` 等在两种模式下都能用。

补充：`XpqAcc` 新增三个 Shizuku 入口 `isShizukuRunning()` / `isShizukuPermissionGranted()` / `requestShizukuPermission(onResult)`，委托给 `AutomationShizuku`（isInstalled/isPermissionGranted/requestPermission）。connect 内部已做权限检测（未授权返回 false）+ UserService 绑定，但不会主动弹授权窗，故授权需宿主先调 requestShizukuPermission。

另封装一步到位 `connectUiAutomation(onLog, onResult)`：内部 use(UIAUTOMATION) → 检测 Shizuku 运行 → 检测/请求授权 → 连接，最终结果经 `onResult(success, reason)` 回调（授权是异步的）。宿主只需一行：`XpqAcc.connectUiAutomation(onLog = {}, onResult = { success, reason -> })`。

ANR 坑（重要）：connect 是阻塞操作（bind Shizuku UserService 的 CountDownLatch.await 最多 10s + UiAutomation.connect 的 mLock.wait 最多 5s），必须在后台线程执行，否则主线程调用直接 ANR。demo 里 connect/clickByText 都是在 `Thread{}` 里调的。已修复：`connectUiAutomation` 内部开 Thread 执行连接、onLog/onResult 都切主线程回调；`use()` 里 accessibilityServiceLiveData.setValue 加了主线程判断（后台线程降级 postValue 防崩）。宿主可在主线程直接调 connectUiAutomation，不会 ANR。

## ProxyAccessibilityService 当 Context 用会 NPE（关键坑）
现象：UiAutomation 模式下 `accessibilityService?.clickByText(...)` 崩溃：
`NullPointerException: ... Context.getApplicationContext() on a null object reference` at `KeyguardUnLock.showClickIndicator`。
根因：`ProxyAccessibilityService` 是直接 new 出来、未被系统 attach 的 AccessibilityService，其 `applicationContext`/`getSystemService`/`resources` 等 Context 方法因 mBase=null 会抛 NPE。库里有地方把 service 参数当 Context 用（尤其「点击/手势轨迹」开关 SHOW_DO_GUIJI 开启时）。
修复：把这些点统一用 appContext 兜底（`runCatching { service.applicationContext }.getOrNull() ?: appContext`）：
- KeyguardUnLock.showClickIndicator（点击轨迹，2252 原崩溃点）
- KeyguardUnLock.showGestureIndicator（手势轨迹）
- KeyguardUnLock 里 6 处 `context = service/accService.applicationContext`（createNaturalSwipePathInfo/computeAutoDuration 等手势计算），脚本批量替换为 runCatching 兜底。
规律：凡是要把 service 当 Context 用（getSystemService/resources/inflate/applicationContext），UiAutomation 模式下都必须用 appContext 兜底，不能直接用 proxyService。

## 视觉指示器（点击轨迹/手势轨迹）在 UiAutomation 下会 BadTokenException（关键坑）
现象：clickByText 不再 NPE，但变成 `WindowManager$BadTokenException: Unable to add window -- token null is not valid`，at `ClickIndicatorManager.ensureWindow`。
根因：ClickIndicatorManager/SwipeTrajectoryIndicatorManager 用 `chooseWindowType()` 返回 `TYPE_ACCESSIBILITY_OVERLAY`（API 28+），该窗口类型**只有真实无障碍服务才有 token**。UiAutomation 模式下传入 appContext（普通 Context）没有该 overlay token，addView 直接 BadTokenException。
正确做法（最终版）：**不要跳过指示器**，而是让窗口类型按上下文回退——`AssistsWindowManager.chooseWindowType()` 改成判断 `SelectToSpeakServiceAbstract.instance != null`：无障碍上下文返回 `TYPE_ACCESSIBILITY_OVERLAY`，否则（UiAutomation）返回普通悬浮窗 `TYPE_APPLICATION_OVERLAY`（需 SYSTEM_ALERT_WINDOW 权限，manifest 已声明）。`showClickIndicator`/`showGestureIndicator` 保留原逻辑，仅把 `service.applicationContext` 用 `runCatching{...}.getOrNull() ?: appContext` 兜底（proxyService 未 attach 时 applicationContext 为 null）。库内已有同范式参考：`DynamicIslandFloatWindow.resolveWindowType`、`MusicControlFloatWindow`（无障碍→accessibility overlay，否则→application overlay）。
注意：`createLayoutParams()` 里仍硬编码 `TYPE_ACCESSIBILITY_OVERLAY`，若后续在 UiAutomation 下用 AssistsWindowManager.add 弹窗也会踩同样坑，需一并改 chooseWindowType()。

## 点击「轨迹显示了但点击没效果」——HumanTouchEngine 依赖 attach()（关键坑）
现象：UiAutomation 模式下 clickByText 能显示点击轨迹（showClickIndicator 执行了），但实际没有点击效果。
根因：`clickByText → gestureClick → HumanTouchEngine.click(x,y) → dispatchAsync`。`dispatchAsync` 开头有 `val currentScope = scope ?: return false` + `val service = serviceRef?.get() ?: return false`；而 `scope`/`serviceRef` 只在 `attach(service)` 里设置，`attach()` 只在**真实无障碍服务的 onServiceConnected** 里被调用。UiAutomation 模式没有这个服务 → attach 从未执行 → scope/serviceRef 全空 → dispatchAsync 直接 return false，手势从未派发。但 `gestureClick` 又无条件 `return true`（忽略 HumanTouchEngine.click 返回值），所以轨迹画了、返回值也是 true，实际没注入事件。
修复：`performGestureInternal` 早已改走 `XpqAcc.dispatchGesture`（门面），service 参数是摆设。故去掉对 attach 的硬依赖——新增 `fallbackScope`（`CoroutineScope(SupervisorJob()+Dispatchers.Default)`），`dispatchAsync` 用 `activeScope() = scope ?: fallbackScope`，删掉 serviceRef 判空；`performGesture`/`performGestureInternal` 去掉 service 参数。这样两条通道都能注入手势。
规律：UiAutomation 模式下凡依赖「无障碍服务 onServiceConnected 才初始化的全局/单例」（如 HumanTouchEngine.attach），都必须改成走 XpqAcc 门面 + fallback，不能直接 return false。

## 点击「轨迹位置对但没效果」——手势注入必须走 shell input（关键坑）
现象：修复 HumanTouchEngine attach 依赖后，轨迹画对了、坐标也对，但点击仍无效果。
根因：`InvisibleAutomation.dispatchGesture` 之前用 `UiAutomation.injectInputEvent` 反射 + `MotionEvent.obtain(downTime,eventTime,action,x,y,0)` 简化重载注入裸事件。该重载 source=0、无 pressure/deviceId，事件被 InputDispatcher 直接丢弃——所以轨迹/坐标都对但触摸根本没派发。
对比 GKD `CompatInputManager`：Android 12+ 直接走 `IInputManager.shellCommand("tap"/"swipe")`（即 shell `input` 命令）；Android 8-11 才用完整 `MotionEvent.obtain`（带 source=SOURCE_TOUCHSCREEN、pressure、deviceId）+ `IInputManager.injectInputEvent`。我们缺的是「shell 注入」这条最可靠的路。
修复：`InvisibleAutomation.dispatchGesture(points,duration)` 改为走已有的 `tap()`/`swipe()`（`mSvc.exec("input tap/swipe")`，shell 身份）：单点或首尾 <5px 视为点击走 tap，否则走 swipe（首尾两点+时长）。删掉 injectMotionEvent/interpolate 死代码。取舍：shell 无法逐点注入拟人化微移轨迹（GKD 同）。
规律：UiAutomation 通道手势注入**优先 shell `input` 命令**（uid 2000，最可靠），不要用 UiAutomation.injectInputEvent 反射 + 简化 MotionEvent.obtain（source=0 无效）。

## 滑动「距离变短/上划解锁不成功」——gestureToPoints 把 startTime 累加进 duration（坑）
现象：点击通了，但滑动（尤其上划解锁 unlockMove）表现像距离变短/没划成功。
根因：`UiAutomationDriver.gestureToPoints` 里 `duration = maxOf(duration, stroke.duration + stroke.startTime)`。`unlockMove→move(path,start=500,duration=500)` 即 `StrokeDescription(path,startTime=500,duration=500)`，startTime 是「延迟启动」而非时长；把 startTime 累加后 duration 变成 1000ms，`input swipe` 滑动慢一倍，上划解锁需快速 fling，慢速拖动不被识别 → 表现「没划够」。
修复：`duration = maxOf(duration, stroke.duration)`，忽略 startTime（input swipe 无延迟概念）。
注意：PathMeasure 采样后只取首尾两点走 `input swipe`，中间曲线点丢失（直线 path 无影响，解锁够用）；若后续要支持拟人化曲线/多段轨迹，需走 GKD Android 8-11 那套完整 MotionEvent.obtain + IInputManager.injectInputEvent。

## 滑动轨迹不显示 + 上划解锁「差一点距离」（坑）
现象：解锁滑动（unlockMove）不显示轨迹，且上划解锁总是差一点。
根因1（轨迹）：`unlockMove→move()`（KeyguardUnLock 1505）里没调 `showGestureIndicator`（只有 moveAwait 才调）。修复：move() 里补 `showGestureIndicator(service, path, duration)`。
根因2（距离）：`input swipe` 是匀速滑动、抬起无惯性；无障碍 dispatchGesture 有 fling 惯性（松手界面继续滑），等效距离更长。同样 800px 上划，无障碍能解锁、UiAutomation 差一点。修复：`InvisibleAutomation.dispatchGesture` 滑动分支把终点沿滑动方向延长 20%（`extX = first.x + dx*1.2`，超界由系统 clamp 到边缘）。
规律：shell input 手势无 fling 惯性，解锁/翻页等 fling 场景需距离补偿。
⚠️ 回退：上一版在 dispatchGesture 里把终点沿方向延长 20%（`extX=first.x+dx*1.2`）导致「滑动完全没反应」——终点被延长到屏幕外（负值），`input swipe` 命令失败 exit!=0。已回退为直接用首尾两点 swipe。教训：终点补偿必须 clamp 到屏幕内，且不能盲目延长；当前改为在 tap/swipe 里加 `diag` 日志（输出 input 命令 + exitCode + stdout/stderr），先定位真实坐标/退出码再决定补偿策略。

## exec() 里 Thread.start() 重复调用 → 命令永远 exit=-1（关键 bug）
现象：加日志后发现 `[swipe] input swipe 805 1909 797 894 600 → exit=-1 stderr=java.lang.IllegalThreadStateException`。
根因：`AutomationUserService.exec()` 里 `outThread.start()` 被**重复写了两次**（第55、56行）。Thread.start() 同一线程只能调一次，第二次抛 IllegalThreadStateException，被 catch 后 exitCode 恒为 -1；errThread 没启动、waitFor() 没执行。命令其实发出去了（process.start()），但结果拿不到，tap/swipe 永远返回 false。
修复：删掉重复的 `outThread.start()`，只保留一次。**accessibilityLibs 原始版也有同样 bug**（automationlib AutomationUserService.kt 同处），一并修复。
规律：这个 bug 是移植时带进来的；凡是「命令执行了但返回值恒 -1/IllegalThreadStateException」，先查 ProcessBuilder 的 start/waitFor/线程 start 是否重复或顺序错。

## 上划解锁「把通知栏拉下来」——input swipe 速度不够（fling 阈值）
现象：exec bug 修复后滑动真正生效，但上划解锁偶尔变成「展开通知栏」而非解锁。
根因：`input swipe` 是匀速滑动、抬起无 fling 惯性；锁屏上划解锁需快速 fling 才识别为「解锁」，速度不够（如 600ms 滑 1015px≈1.7px/ms）被判定为慢速拖动 → 展开通知栏。无障碍 dispatchGesture 有加速度+fling 惯性所以能解锁。
修复：`InvisibleAutomation.dispatchGesture` 滑动分支把时长减半并封顶 300ms（`(durationMs/2).coerceIn(80,300)`），提高松手速度接近 fling。
规律：shell input 手势模拟 fling 场景（解锁/翻页/下拉），靠「减时长提速度」而非「延长距离」；延长距离会导致坐标越界 input 命令失败。

## 上划解锁仍展开通知栏——终点只到屏幕 35%，需滑到屏幕边缘
现象：减时长后仍展开通知栏。日志 `input swipe 805 1909 797 894 600`：终点 y=894 只到屏幕 35% 处就停。input swipe 无 fling 惯性，滑到 35% 就停，锁屏判定上划不足 → 停在通知栏中间态；无障碍 dispatchGesture 松手有惯性会继续滑到顶。
修复：① 连接成功后经 shell `wm size` 缓存屏幕物理尺寸（`Physical size: WxH` 正则解析到 screenW/screenH）；② `dispatchGesture` 滑动分支把终点沿滑动方向延长到屏幕边缘并 clamp（`dx>0 → screenW-1`，`dy<0 → 0` 等），同时减半时长。这样上划一定滑到顶触发解锁。
关键：延长终点必须 clamp 到屏幕内（0..screenW/H），之前 20% 延长失败是因为没 clamp + 坐标越界。
⚠️ 用户反馈「不要滑动到顶」→ 已回退：终点延长到屏幕边缘（y=0）过于激进，会干扰其它滑动场景。回退为**终点不变 + 只减半时长提速**（`(durationMs/2).coerceIn(80,300)`），screenW/screenH 字段与 wm size 获取逻辑一并删除。解锁 fling 的速度/距离权衡仍待真机确认。

## 锁屏上轨迹不显示——悬浮窗缺 FLAG_SHOW_WHEN_LOCKED
现象：解锁滑动 + 解锁后输密码点击，轨迹都不显示（非锁屏界面点击轨迹能显示）。
根因：UiAutomation 模式下窗口类型是 TYPE_APPLICATION_OVERLAY（chooseWindowType 判断 instance==null 时返回），但 ClickIndicatorManager / SwipeTrajectoryIndicatorManager 的 LayoutParams 都没加 `FLAG_SHOW_WHEN_LOCKED`，锁屏（keyguard）时普通悬浮窗被系统隐藏。
修复：两个 Manager 的 ensureWindow 里 flags 都加 `FLAG_SHOW_WHEN_LOCKED`。
规律：锁屏上要显示悬浮窗，必须加 FLAG_SHOW_WHEN_LOCKED（TYPE_APPLICATION_OVERLAY 在 keyguard 默认隐藏）；无障碍模式的 TYPE_ACCESSIBILITY_OVERLAY 则天然能覆盖锁屏。

## 全库悬浮窗类型统一为兼容模式（无障碍不可用回退普通悬浮窗）
需求：库内所有悬浮窗类型改兼容模式——无障碍可用走 TYPE_ACCESSIBILITY_OVERLAY，否则回退 TYPE_APPLICATION_OVERLAY。
关键判断标准：**`SelectToSpeakServiceAbstract.instance != null`（真实无障碍服务实例）**，不能用全局 `accessibilityService` 变量——后者在 UiAutomation 模式下被 `XpqAcc.use()` 指向 proxyService（非 null 假实例），会误判为「无障碍可用」。
改动清单：
- `AssistsWindowManager.createLayoutParams()`：硬编码 TYPE_ACCESSIBILITY_OVERLAY → `chooseWindowType()`。
- `FloatToastManager` / `CodeToastManager`：import 改 `SelectToSpeakServiceAbstract`；context 改 `instance ?: appContext`；判断 `accessibilityService != null` → `instance != null`。
- `FloatingImeWindow`：show 里加 `val realService = instance ?: accessibilityService`，context 用 realService，判断改 realService。
- `JieSuoUtils` 两处（showDialogZuobiao 的 controlParams/targetParams）：硬编码 → `AssistsWindowManager.chooseWindowType()`。
- `LogWrapper` 三处 dialog、`DynamicIslandFloatWindow` 两处 dialog：硬编码 setType → `AssistsWindowManager.chooseWindowType()`。
已兼容无需改：`AliveUtils`（ctx is AccessibilityService，调用点传真实 service 或前台服务）、`XpqOverlayHelper`、`MusicControlFloatWindow.resolveWindowType`、`DynamicIslandFloatWindow.resolveWindowType`（本就有 svc!=null fallback）。
规律：判断「无障碍是否可用」一律用 `SelectToSpeakServiceAbstract.instance != null`；UiAutomation 模式下全局 accessibilityService 变量是 proxyService，绝不能当 Context 用（getSystemService/inflate 会 NPE）。
