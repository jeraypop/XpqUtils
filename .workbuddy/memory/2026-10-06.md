## 加固后 Shizuku 连接失败修复（19:20）
- 现象：宿主 App 加固（加壳）后 `Shizuku 模式 连接失败：bind() 返回 null：Shizuku UserService 绑定超时或被拒绝`；不加固正常。
- 根因：UserService 子进程由 Shizuku 以 `app_process` 拉起，需加载宿主 APK 的 dex 并创建宿主 Application；
  加固后壳 Application 在无 UI 环境崩 / 真实 dex 被加密 → 子进程起不来 → bind 超时。
  而原代码把 bind 失败当**致命错误**（`return false`），但注册其实早在 App 进程内完成
  （ProxyUiAutomationConnection + ShizukuBinderWrapper），UserService 只剩 exec 一个职责。
- 修复（InvisibleAutomation.kt，单文件多处串行）：
  1. `connectRetry`：bind 失败不再中断，降级为 log 警告并继续 [3/3]；新增 `userServiceUnavailable`
     记忆位，后续连接直接跳过 bind（避免每次白等十几秒）。
  2. `exec()` 改为统一入口：`mSvc` 优先，否则 `execViaNewProcess`（反射 private 的 `Shizuku.newProcess`，
     `sh -c` + 读流 + ShellResult）。所有 7 处 `mSvc?.exec(` 改为 `exec(`。
  3. `clearFocusedText()` 去掉 `if (mSvc == null) return false` 前置拦截。
  4. `tap()` 的 reflect 分支在 `mSvc == null` 时回退 `input swipe`（不再直接 false）。
- 踩坑：`Shizuku.newProcess` 在 api:13.1.5 是 **private static**，直接调用编译报
  `e: Cannot access 'static fun newProcess(...)': it is private in 'rikka.shizuku.Shizuku'`，改反射解决。
- `AccessibilityEnableHelper` 全部经 `InvisibleAutomation.exec`，自动受益（shell 路径加固后仍可用）。
- BUILD SUCCESSFUL（:accessibility:assembleDebug）。
- 待用户验证：重新集成 → 加固 → 真机确认连接与 shell 功能；首次连接仍会等一次 bind 超时后才降级。

## 去掉对私有 Shizuku.newProcess 的硬依赖（20:50）
- 起因：用户担心 `Shizuku.newProcess` 是私有方法，后续 Shizuku 版本可能移除。
- 调研结论：
  1. `UiAutomation.executeShellCommand`（公开 SDK API）在本架构下**走不通**——我们的 UiAutomation connection 是自研的
     ProxyUiAutomationConnection，只实现了 connect(=FIRST_CALL_TRANSACTION)/disconnect(+1) 两个事务，没有 executeShellCommand 分支。
     且该 API 在 AOSP 走真实 UiAutomationConnection（system_server 侧），我们无法提供。
  2. 正解：Shizuku **官方公开 AIDL** `moe.shizuku.server.IShizukuService.newProcess(String[],String[],String) → IRemoteProcess`。
     `dev.rikka.shizuku:aidl` 被 api 的 pom 以 compile 传递依赖带入，编译期直接可用（无需额外声明）。
- 实现（InvisibleAutomation.execViaNewProcess 改为双路径）：
  ① AIDL 优先：反射 `ShizukuProvider.getBinder()`（编译期 Unresolved，非 public）→ `IShizukuService.Stub.asInterface` → `newProcess` → 读 IRemoteProcess；
  ② 反射 `Shizuku.newProcess` 兜底（保留 newProcessMethod）。
  再兜一层：obtainShizukuService 里若 getBinder 不可用，回退反射 `Shizuku.requireService()`。
- 踩坑：`IRemoteProcess.getInputStream()/getErrorStream()` 返回的是 **ParcelFileDescriptor**（不是 InputStream），
  必须用 `ParcelFileDescriptor.AutoCloseInputStream(pfd)` 包装后才能读。
- 稳定性论证：aidl 是 Shizuku 单独版本化的 maven 工件、且是 server↔client 有线协议（改签名会连带升 aar 版本），
  比 Java private 方法稳得多；反射保留作最后兜底。
- BUILD SUCCESSFUL。

## UserService 绑定异步化（21:10）
- 用户反馈：加固后首次连接仍等很久，"是不是没生效"。
- 定位：降级逻辑本身是生效的（bind 失败→置 userServiceUnavailable→继续注册），但 bind 仍在
  关键路径上——`connect(timeoutMs=15_000L)` 的 timeoutMs 直接传给了 `AutomationShizuku.bind`，
  所以加固下必须等满 15s 超时才降级，“第一次慢”由此而来；且 timeoutMs 其实只被 bind 使用
  （UiAutomation 注册没有超时参数）。
- 修改（InvisibleAutomation.kt）：
  1. connectRetry 的 bind 段改为：userServiceUnavailable→跳过；isUserServiceBound()→同步复用
     （0L 超时，立即返回缓存）；否则 `bindUserServiceAsync(...)` 后台绑定，不阻塞。
  2. 新增 bindUserServiceAsync()：daemon Thread，成功且 isConnected 时填 mSvc + 打 [2/3] 日志；
     失败置 userServiceUnavailable；连接已断则只留 AutomationShizuku 缓存；userServiceBinding
     防重入（重连/重试期间不会并发 bind 两次）。
  3. connect() 加 KDoc 说明 timeoutMs 只约束后台绑定。
- AutomationShizuku 新增 isUserServiceBound()（零阻塞查询）。
- UiAutomationDriver.connect 加注释说明 15000L 的语义变化。
- 日志顺序变化：`[2/3] UserService 已就绪` 会在 `[3/3] 连接成功` 之后异步出现（成功时）；
  加固下则是 15s 后在后台打一条降级提示，不影响用户等待。
- BUILD SUCCESSFUL。

## 「能不能自动判断宿主加固」调研 + 快速失败实现（21:15-21:35）
- 调研手段：javap 反汇编 dev.rikka.shizuku:api:13.1.5 + DeepWiki Shizuku-API 文档。
- 硬事实：
  1) api 里 ShizukuServiceConnection extends IShizukuServiceConnection.Stub，connected(binder) 时
     存 binder + linkToDeath；dying → died() → MAIN_HANDLER.post → 遍历调 onServiceDisconnected。
  2) **linkToDeath 只在成功 connected 之后建立** → 「attach 前就崩」不产生 died()。加固宿主正是
     这种（壳 Application 在 app_process 环境创建即崩）→ 仍要等 bind 超时。
  3) 服务端 UserServiceRecord 有 30s startup timeout（> 我们的 10s/15s，无冲突）。
  4) 回调投递到主线程 → bind() 在主线程调用必然超时（既存陷阱）。
  5) 旧版 server 的 unbindUserService(remove=false) 有 connections[] 未清空的 bug（commit 635b1c4），
     会导致回调多次触发；本库不调 unbindUserService，不受影响；且我们的计数/标志是幂等的。
- 实现（AutomationShizuku.kt，串行 4 处）：import AtomicBoolean；KDoc 加「禁止主线程调用」警告；
  新增 diedBeforeConnected 标记；onServiceDisconnected 里 ref.set(null)+标记+countDown；
  await 后分流日志（超时 / 秒退）并只在 svc==null 时置 userServiceUnavailable（在 async 层）。
- 效果：UserService「起来后死掉」现在立即返回失败，不再白等满超时；加固「attach 前崩」场景仍走超时
  （但已在后台，用户无感）。日志能区分「超时」与「秒退」，可作为是否加固的诊断线索。
- 未实现（等用户定）：壳特征扫描（不凭记忆写特征表）、宿主自报真实 Application 类名比对（需一行）。
- BUILD SUCCESSFUL。

## 消除「感知到的慢」：三处延迟修复（21:28-21:30）
背景：用户问「现在是不是后台等一次？还能明显感知慢吗」。查代码后确认连接主链路已不吃 bind 的
15s，但仍有 3 处会被感知，用户同意一起改：
1. **后台绑定超时 15000L → 3000L**（`InvisibleAutomation.connect` 默认值 + `UiAutomationDriver.connect`
   显式传参）。原因：`userServiceUnavailable` 只在内存、进程重建后首次连接会再起后台绑定，加固机
   走满超时 → 15s 后才在日志面板打出失败行，用户误以为连接卡住（其实 onResult(true) 几百 ms 就回调了）。
   3s 覆盖正常机型冷启动绑定，同时把日志静默期压短。注释里标明这是**体感上限，非平台限制**。
2. **`clearFocusedText()` 在 API<30 的 120 次 fork → 合并为单条 shell 脚本**。
   原实现 `repeat(120) { exec("input keyevent 67") }`：UserService 未绑定时每次 exec 都走
   `execViaNewProcess` fork 一个 sh（约 100~300ms），累计 12~36 秒，表现为「清空输入框卡死」。
   改为 `exec("input keyevent 123; i=0; while [ \$i -lt 120 ]; do input keyevent 67; i=\$((i+1)); done")`，
   一次 fork。API 30+ 路径本来就是 2 条命令，未动。
3. **`dispatchGesture` 里硬编码的 `SystemClock.sleep(1000L)`（滑动前固定停 1s）已删除**。
   该值无任何依据、也非 shell 命令所需，只让每次滑动多等 1 秒；需要稳定等待应由调用方在业务层控制。
- 顺带确认的既有事实：`exec()` 在 mSvc==null 时统一走 newProcess 直连，所以首次连接后立刻发
  shell 命令（tap/swipe/inputText）各 fork 一次（单次 100~300ms，属「略慢」），绑定成功后自动转复用。
  `tapNew()` 因每个 `input motionevent` 是一条命令，一次点击 fork 3~5 次，是受此影响最大的一条路径。
- 编译 `:accessibility:assembleDebug --offline`：BUILD SUCCESSFUL（仅剩一条既有 warning：
  InvisibleAutomation.kt:517 `clazz!!` 非空断言多余，未动）。
