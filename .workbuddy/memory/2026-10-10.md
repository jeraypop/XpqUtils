# 2026-10-10

## 宿主侧「启动恢复引擎模式」的标准三段式（XpqAcc）
代码形态：
```kotlin
XpqAcc.setBridgeFallbackProvider { SelectToSpeakService() }
if (XpqAcc.findAccessibilityServiceSubclass() == null) {
    XpqAcc.saveEngineMode(EngineMode.UIAUTOMATION)
}
XpqAcc.applyEngineMode(XpqAcc.loadEngineMode(), SelectToSpeakService()) { success, reason ->
    Log.d("XpqAcc", "启动恢复引擎模式: success=$success reason=$reason")
}
```
要点与坑：
1. `setBridgeFallbackProvider` 收的是**工厂 lambda**，只在 `autoBridgeAccessibilityEvent()` **无参**调用、
   且反射不到宿主无障碍子类时才会 `invoke()`。而 `applyEngineMode` → `connectUiAutomation` 内部走的是
   `autoBridgeAccessibilityEvent(bridgeFallback)`（**显式实参**，XpqAcc.kt:253）。
   → 这段代码里的 provider 实际上**几乎用不到**，属于保险；真正的兜底是第 2 个实参 `SelectToSpeakService()`。
2. `findAccessibilityServiceSubclass()`：`PackageManager.GET_SERVICES` 查声明了
   `BIND_ACCESSIBILITY_SERVICE` 的服务 → `Class.forName` → 反射 `newInstance` → 强转
   `SelectToSpeakServiceAbstract`；任一环节失败返回 null。**每次调用都会 new 一个实例**（会跑构造函数）。
3. 无无障碍服务时 `saveEngineMode(UIAUTOMATION)` 会**静默覆盖**用户此前保存的无障碍模式，无提示；
   用途是避免后面 apply 走进必然失败的分支。
4. `applyEngineMode` 的 UiAutomation 分支**未传 activity** → 连接失败**不会弹引导对话框**，只经
   `onResult(false, reason)` 回调。宿主这里只写 `Log.d`，用户完全无感。要可感知就得把 activity 传进去。
5. 分支语义：`ACCESSIBILITY_SERVICE` = `useAccessibilityService()` 纯切通道 + `ok = instance != null`
   （失败 reason = "请先在系统设置开启无障碍服务"）；`UIAUTOMATION` = `connectUiAutomation()`（内部后台线程，主线程调用安全），
   成功后自动 `autoBridgeAccessibilityEvent` + 执行 `postConnectShellCommand`（默认 WRITE_SECURE）。
