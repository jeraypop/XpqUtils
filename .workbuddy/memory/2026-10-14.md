## 调研：`onConfigurationChanged` 在双通道下的可用性（只调研，未改代码，等用户选方案）
- AOSP `sources/android-36` 原文核实：
  - `Service.onConfigurationChanged(Configuration)` 是**空实现**（`android/app/Service.java:540`），
    **不读 mBase** → 手动 new 的 AccessibilityService 实例调 `super.onConfigurationChanged()` **不会 NPE**
    （与 `ContextWrapper` 那类读 mBase 的方法不同）。`AccessibilityService` 未 override 它。
  - 但宿主 override 内若访问 `resources` / `applicationContext`，未 attach 的实例仍会 NPE。
- 触发条件：系统只对**运行中且被系统 attach 的 Service** 回调。
  - 无障碍模式 → 真实实例，回调**会**来（宿主当前是空实现，等于旋转后无任何适配）。
  - **纯 UiAutomation 模式 → 回调永远不来**：App 进程内没有 attach 的实例，`proxyService` / `bridgedHandler`
    都是手动 new（不走 `ActivityThread.handleCreateService`，不在 mServices 列表）。
    只有 `KEY_UIA_ENABLE_HOST_ACC=true` 双活时，真实的宿主无障碍实例才会收到。
- 宿主现状：`app/.../service/AccessibilityServiceImp.kt:33` 的 override 只调 super，空壳。
- 待选方案（均未实施）：
  - A（推荐）库加通道无关钩子 + `appContext.registerComponentCallbacks` 转发；连接时注册、`disconnect()`
    / `onUiAutomationDestroy` 时**必须成对注销**（进程级注册，漏注销会泄漏 + 断开后仍回调）。
  - B 宿主自己在 `Application.onCreate` / `onUiAutomationReady` 注册（零库改动，但易漏注销，且无障碍模式下
    与 Service 自身回调可能重复触发，需去重）。
  - C 库直接把配置变化转发到 `bridgedHandler.onConfigurationChanged()` —— **宿主零改动**（既有 override 自动生效），
    需给桥接实例补一次 `attachBaseContext(appContext)`（同 proxyService 的 `ensureAppContext()` 手法）。
- 旋转后需要重算的对象（库内 `displayMetrics` 基本都是**当场读**、无静态缓存，所以重点不是清缓存，
  而是**重排已展示的悬浮窗 + 已持久化的坐标参数**）：
  `DynamicIslandFloatWindow`（166/198/223/234/245/335/571）、`FloatingImeWindow`(79-81)、
  `MusicControlFloatWindow`(80-82)、`AssistWindowManager`(36)、`ForegroundWindowUtils`(207)、
  `KeyguardUnLock`（滑动路径按 0.75h/0.35h 比例、`KEY_APP_LOCK_POINTS` 持久化坐标会随旋转失效）。

## 方案 A 可行性确认（用户担心"库里拿不到 Application"）
- **库里能拿到 Application**：`LibCtxProvider`（ContentProvider）的 `onCreate` 里就有
  `(appContext as? Application)?.registerActivityLifecycleCallbacks(...)`（第 129 行），先例已在。
- **更好的是根本不需要强转**：AOSP `Context.java:966-968` 原文
  `public void registerComponentCallbacks(ComponentCallbacks callback) { getApplicationContext().registerComponentCallbacks(callback); }`
  —— 任何 Context 调用都会落到 Application 上（进程级）。`LibCtxProvider.appContext` 本身就是
  `context!!.applicationContext`（attach 过的），直接调即可。
- 三个约束：① 文档明确 **必须** `unregisterComponentCallbacks` 成对注销；② 注册只对**调用它的那个进程**
  生效（Application 每进程一份）；③ 注册点与"UiAutomation 连接成功"绑定最稳（天然落在正确进程），
  重复连接要先注销旧的回调再注册（幂等）。
- 进程现状：app manifest 里的无障碍服务 `SelectToSpeakService`（67-80 行）**没有** `android:process`
  → 与主进程同进程；`UiAutomation` 连接也由主进程发起 → 单点注册即可。
- 推荐落地：`SelectToSpeakServiceAbstract` 新增 `open fun onConfigChanged(Configuration) {}`，并在库内
  `override fun onConfigurationChanged()` 里 `super` + 转发到它 → **无障碍模式下系统回调自动汇入同一钩子**，
  宿主现有的 `AccessibilityServiceImp.onConfigurationChanged`（只调 super）无需改动即可闭合到新钩子；
  UiAutomation 模式由库注册的 ComponentCallbacks 转发 `currentService()?.onConfigurationChanged(cfg)`。
  双活去重：转发前判 `SelectToSpeakServiceAbstract.instance == null`（有真实实例时系统自己会调，否则宿主收两次）。

## 追加调研：`onLowMemory` / `onTrimMemory` 挂在同一套转发里有没有价值（结论：只值得挂 onTrimMemory）
- `onLowMemory()` **API 34 起永不调用**，源码注释原文：
  `ComponentCallbacks.java:58-66` — "Since API level 14 this is superseded by onTrimMemory.
  **Since API level 34 this is never called.**" → 挂上去是死代码，只对 Android 13 及以下有意义（minSdk 24）。
- `onTrimMemory(level)` 共 7 档，**5 档已废弃**，注释均为 "Apps are not notified of this level since API level 34"：
  `RUNNING_MODERATE`(5)、`RUNNING_LOW`(10)、`RUNNING_CRITICAL`(15)、`MODERATE`(60)、`COMPLETE`(80)。
  **只有 `UI_HIDDEN`(20) 与 `BACKGROUND`(40) 未被标记废弃**。
- `ActivityThread.handleTrimMemory(int)`（:7412-7423）有前置 return：
  `skipBgMemTrimOnFgApp()`（aconfig `android.app.Flags.skipBgMemTrimOnFgApp`，见 ActivityThread:21 import）
  且 `mLastProcessState <= PROCESS_STATE_IMPORTANT_FOREGROUND` 且 `level >= TRIM_MEMORY_BACKGROUND(40)`
  → **直接 return，一个回调都不派发**。无障碍/保活这类"前台型"进程基本命中此条件，
  **实际能稳定等到的只有 `UI_HIDDEN` 一档**。
- 派发链：`collectComponentCallbacks(true)` = mAllApplications + mActivities(未 finish) + **mServices**
  （ActivityThread:6648-6650）→ Service 确实在名单里 ⇒ 无障碍模式下两个回调都会到；UiAutomation 模式下依旧静默。
- **本项目特有陷阱**：可见面是 WindowManager 悬浮窗而非 Activity。`UI_HIDDEN` 在宿主 Activity 一退/锁屏就来，
  此时保活 + 悬浮窗 + 自动化都还在正常工作 → 若按官方文档"释放 UI 大对象"，会放掉正在使用的东西。
- 库内真正值得释放的具体对象（都不适合等系统信号，更适合用完即清 / 定时清）：
  `LogWrapper.logCache`（上限 5000 字符的 StringBuilder）、`MusicCache`、
  `NetworkCheckHelperSmart.clearCache()`、`ScreenshotHelper` 里 `Bitmap.createBitmap` 的位图、
  `ClickIndicatorManager` / `SwipeTrajectoryIndicatorManager` 的指示器窗口。
- 建议：**只挂 `onTrimMemory` 且只做"转发"**（库里不做任何释放）；`onLowMemory` 不挂（或挂上并在注释里写明
  仅作老设备兜底、API 34+ 永不触发）。

## 实现：通道无关的「配置变化 / 内存回收」（方案 A，已落地）
- **决策修正（与上一节的计划不同）**：原计划在 `SelectToSpeakServiceAbstract` 加 `onConfigChanged` /
  内存钩子两个**新**方法，实现时发现多余 —— 库直接转发到**服务方法本身**
  （`bridgedHandler.onConfigurationChanged(cfg)` / `.onTrimMemory(level)`），宿主**已有的**
  `override fun onConfigurationChanged` 零改动即生效；若走新钩子，反而要求宿主再加一个 override。
- `XpqAcc.kt`：
  - 新增 `uiAutomationComponentCallbacks: ComponentCallbacks2`（两个方法 → `forwardToBridge`；
    `onLowMemory` 空实现 —— 父接口已 `@Deprecated`，必须 `@Suppress("OVERRIDE_DEPRECATION")`，
    否则新增一条编译 warning）。
  - 新增 `componentCallbacksRegistered` 标志 + `register/unregisterUiAutomationComponentCallbacks()`（幂等）。
  - **注册点**：`autoBridgeAccessibilityEvent()` 中 `bridgeAccessibilityEvent(handler)` 之后 ——
    保证转发目标 `bridgedHandler` 已就位，且宿主手动调用 autoBridge 也被覆盖。
  - **注销点**：`teardownUiAutomationBridge()` 开头 —— 被 `disconnect()` / `use()` 切走 UiAutomation /
    `connectUiAutomation` 的连接前清理三处共用。进程级注册，必须成对。

    （双活去重，否则真实实例 + 桥接实例各收一次）；`bridgedHandler ?: return`；`runCatching` 包裹。
  - 新增 import：`android.content.ComponentCallbacks2`、`android.content.res.Configuration`。

  **不无条件透传 super** —— `ContextWrapper.onTrimMemory` 读 `mBase`，手动 new 的桥接实例在 appContext
  未就绪时 `mBase == null` 会 NPE；仅 `baseContext != null` 时透传。`onConfigurationChanged`

## 修正（同日）：砍掉 trim 转发，只保留 config 转发
- **用户质疑**：「onLowMemory / onTrimMemory 都有局限性，收益不大，不如去掉」——**基本成立**，据此动手。
- **核实到的新事实（两边原先都漏了）**：**`Application` 本来就会收到这两个事件，两种通道都收得到**
  - `ConfigurationController.handleConfigurationChangedInner:225` → `collectComponentCallbacks(false)`；
    `ActivityThread.handleTrimMemory:7390` → `collectComponentCallbacks(true)`。两者都收集
    **`mAllApplications` + `mServices`**（ActivityThread:6636-6656）。⚠ config 那条 `includeUiContexts=false`
    ⇒ **不含 Activity**（Activity 走 `performActivityConfigurationChanged` 另一条路）；
    trim 那条 `(true)` 含 Activity。
  - ⇒ 宿主 override `Application.onConfigurationChanged` / `Application.onTrimMemory` 即可，**不需要库做任何事**。
- **因此库这条链路的真正价值重定位**：不是「宿主收不到」，而是
  ① 把事件送到**宿主服务实例**（自动化状态所在的那个对象），不用在 Application 里搭桥（跨组件）；
  ② **复活宿主已有的 `AccessibilityServiceImp.onConfigurationChanged`** —— 它在纯 Shizuku 模式下
     一直是死代码且不报错。库承诺「`use()` 选通道后业务代码零改动」，这条属于库该修的范围。
- **决定：去掉 trim 转发**（无消费方：`LogWrapper.logCache` 自封 5000 上限、`MusicCache` /
  `NetworkCheckHelperSmart` 是库内可自清的、截图位图在 Activity 侧；而 UI_HIDDEN 宿主从
  `Application`/`Activity.onTrimMemory` 直接拿得到）。具体动作：
  - 回调对象 `object : ComponentCallbacks2` → **`object : ComponentCallbacks`**。这既是精简，
    也是**用类型表达决定**：`Application.dispatchTrimMemory` 按 `instanceof ComponentCallbacks2` 过滤
    （ComponentCallbacksController:106-112），换成 `ComponentCallbacks` 后 trim 在类型层面就不经过本库。
    注意 `ComponentCallbacks` 仍需实现已废弃的 `onLowMemory()` → 保留 `@Suppress("OVERRIDE_DEPRECATION")`。
  - 删掉 `SelectToSpeakServiceAbstract.onTrimMemory` override 与 `XpqAcc.forwardToBridge` 的 trim 调用
    ⇒ **`SelectToSpeakServiceAbstract.kt` 回到零改动**。
  - 副作用参考：`Application.onConfigurationChanged/onTrimMemory/onLowMemory` 都是 `@CallSuper`
    （Application.java:277/282/287）且内部才遍历 `mComponentCallbacks` —— 宿主若 override 了 Application
    的同名方法却不调 super，别人注册的回调就收不到；库自己注册可绕开这层依赖。
- 验证：`./gradlew :accessibility:compileDebugKotlin :app:compileDebugKotlin --offline --no-daemon`
  → **BUILD SUCCESSFUL in 52s**，无新增 warning。
- ⚠ **踩坑**：KDoc 里写了 `（RUNNING_*/MODERATE/COMPLETE）`，其中的 **`*/` 把块注释提前闭合** →
  后面整段文本被当成代码，报 26 条 `Syntax error: Expecting member declaration`。块注释内不要出现 `*/`，
  写全常量名（`RUNNING_MODERATE / RUNNING_LOW / ...`）。

## 宿主侧「还需做什么」的结论（同一轮答复，已核实调用链）
- **验证通过**：宿主 `app/.../service/AccessibilityServiceImp.kt:33` 的 override **就是接收点**，因为
  manifest 声明的无障碍服务是 `com.google.android.accessibility.selecttospeak.SelectToSpeakService`
  （app manifest:68），而 `class SelectToSpeakService : AccessibilityServiceImp()`（app 侧第三次继承，
  `SelectToSpeakService.kt:13`）；链 = SelectToSpeakService → AccessibilityServiceImp → FirstAccessibility
  → SelectToSpeakServiceAbstract。库转发用 `forwardToBridge { it.onConfigurationChanged(cfg) }`，
  `it` = `bridgedHandler` = 从 manifest 反射 new 的那个实例 → 虚分派必然命中该 override。
- ⇒ **宿主编译层面零改动即生效**，唯一要做的是**往那个空 override 里写适配代码**（不写则收益为零）。
- 三条顺手可用的前提：① 主线程派发（`ConfigurationController` 在主线程）→ 可直接碰 UI/WindowManager；
  ② 桥接前已 `ensureAppContext()` → override 内 `resources` / `applicationContext` / `getSystemService` 可用；
  ③ 库的 `runCatching` 会**吞掉** override 抛出的异常（不崩、无提示）→ 调试期自己 try/catch + 打日志。
- **宿主不要做的事**：别再自己 `registerComponentCallbacks`（库已注册，会收两遍）；不要用
  `Application.onConfigurationChanged` 再转发一次（重复；且该方法 `@CallSuper`，override 忘了 super
  会把库注册的回调一并掐掉）；新逻辑别写在不在上链的类里。
