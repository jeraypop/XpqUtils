## 修复 AAPT：`<queries>` 里不能写只带 android:name 的 `<provider>`
- 报错：`accessibility/build/intermediates/merged_manifest/debug/processDebugManifest/AndroidManifest.xml:28:9-66:
  AAPT: error: <provider> is missing required attribute 'android:authorities'.`
- 根因：`accessibility/src/main/AndroidManifest.xml` 的 `<queries>` 里被加了一行
  `<provider android:name="rikka.shizuku.ShizukuProvider"/>`（git diff 确认是本轮未提交的新增）。
  **`<queries>` 内的 `<provider>` 是按 authority 匹配的，`android:authorities` 是必填属性**，
  `android:name` 这个属性在这个位置根本不认 → 既编不过，也起不到任何作用。
- 为什么可以安全删掉（不是"先删了再说"，是核实过不需要）：
  - 反编译 `dev.rikka.shizuku:provider:13.1.5` 的 `classes.jar` 看 `ShizukuProvider` 字节码，
    其 `requestBinderForNonProviderProcess` 拼的是 `content://` + **`context.getPackageName()`** + `.shizuku`
    → 客户端访问的是**自己包里的** provider（provider 由消费方清单声明，provider AAR 本身不声明），
    同包不受 Android 11+ 包可见性过滤；
  - 跨包场景（找 Shizuku App / 改包名 fork）由已有保险覆盖：`<package>` 两个官方包名 +
    `<intent> MAIN/LAUNCHER`（这才是"按类名扫 fork"能成功的原因）。
  - 该 AAR 的 `AndroidManifest.xml` 只含 `moe.shizuku.client.V3_SUPPORT` meta-data 与
    `moe.shizu.manager.permission.API_V23` 权限，**不含 `<provider>` 声明** —— 声明责任在消费方。
- 改动：
  1. 删掉那一行，原地留一段注释说明「为什么不能这么写 / 为什么本库不需要」
     （注释里刻意**不写**带尖括号的 provider 标签，避免以后 grep 或工具误判；只用文字 + 属性名描述）。
  2. `AutomationShizuku.kt:191-193` 那条**误导性注释**一并修正：原文让人「在 <queries> 里声明其包名
     或 `<provider android:name="rikka.shizuku.ShizukuProvider"/>`」，改为指向真正生效的
     `<intent> MAIN + LAUNCHER` 与 `<package>`。
- 验证（**注意：这次必须跑到清单/资源阶段，`compileDebugKotlin` 不会碰清单**）：
  `./gradlew --offline :accessibility:processDebugManifest :app:processDebugManifest` → BUILD SUCCESSFUL；
  再 `./gradlew --offline :accessibility:assembleDebug :app:assembleDebug` → **BUILD SUCCESSFUL in 8s**，
  产出 `app/build/outputs/apk/debug/app-debug.apk`（18,546,086 bytes，00:17）。
  合并后清单里 `<queries>` 内已无 provider 元素；`<application>` 内那条带
  `android:authorities="${applicationId}.shizuku"` 的 ShizukuProvider 保持不变（app 模块清单 95-98 行同样保留）。
- 手法备忘：AAPT 的 `<queries>`/清单类报错只能靠 `processDebugManifest` / `processDebugResources` /
  `assembleDebug` 暴露，**只编译 Kotlin 永远看不到** —— 以后改清单要顺带跑一次 `processDebugManifest`。

## 真需求浮出水面：manager 并入「另一个宿主」时，跳不过去管理器界面
- 用户说明动机：「另一个宿主充当 shizuku 管理器的角色，然后就提示找不到 shizuku 应用」
  —— 上面那行 `<queries><provider>` 就是他为此尝试的（无效）。
- **根因（用 AAR 清单核实，不是猜）**：`com.github.jeraypop.Shizuku:manager:1.3.0` 的 AAR 清单里，
  `moe.shizuku.manager.MainActivity` 是 `android:exported="true"` 但**没有任何 `<intent-filter>`**。
  于是：
  - `queryIntentActivities(ACTION_MAIN + CATEGORY_LAUNCHER)` **永远扫不到它**（原 `openShizuku` 的 2a 分支）；
  - 那个宿主的 `getLaunchIntentForPackage(pkg)` 返回的是**宿主自己的启动页**，不是管理器界面；
  - 若那个宿主没有任何启动页 → 连包都打不开 → 就是用户看到的「未找到 Shizuku 应用」。
  唯一可行路径 = **已知包名 + 已知类名，按 `ComponentName` 显式跳转**。
- 顺带核实：`dev.rikka.shizuku:aidl:13.1.5` 的 `IShizukuService` **没有** `getManagerPackageName()`
  之类的方法（方法表：attachApplication / attachUserService / addUserService / removeUserService /
  checkPermission / checkSelfPermission / requestPermission / getVersion / getUid / newProcess /
  getSELinuxContext / getSystemProperty / setSystemProperty / exit / isHidden / dispatchPackageChanged /
  getFlagsForUid / updateFlagsForUid …）→ **无法向 server 询问管理器包名**，只能由宿主告知。
- 改动（`AutomationShizuku.kt`）：
  - 新增 `private data class ManagerApp(pkg, cls)` + `registeredManagerApps`（`CopyOnWriteArrayList`，
    替换原 `standaloneExtraPackages: MutableList<String>`，语义从「包名」升级为「包名 + 可选类名」）
    + `managerCandidates = registered + KNOWN_SHIZUKU_PACKAGES.map { ManagerApp(it, null) }`。
  - `openShizuku` 顺序重排：① 本包内 `Class.forName` 直开（不变）→ ② **新 2a：候选应用按
    `ComponentName(pkg, cls ?: MANAGER_MAIN_ACTIVITY)` 显式跳转** → ③ 2b 扫带启动页的活动（原 2a）→
    ④ 2c 退到候选应用的启动页（原 2b 去掉注册项部分）。
  - 新增私有 `startComponent()`（显式组件跳转，异常吞掉返回 false，与 `startActivity` 分开）。
  - `addStandaloneShizukuPackage(pkg: String)` → `addStandaloneShizukuPackage(pkg: String, activityClass: String? = null)`
    （`@JvmOverloads` 保住 Java 侧单参重载，旧调用不破）。
- ⚠ **包可见性结论**：本库 `<queries>` 里那条 `<intent> MAIN + LAUNCHER` 使所有**带启动页**的应用可见，
  所以「另一个宿主有启动页」时，显式组件跳转**不需要**宿主再声明 `<queries><package>`；
  只有对方连启动页都没有时才需要额外声明。已写进 `openShizuku` KDoc。
- 待用户提供：那个宿主 App 的**包名**（workspace 兄弟项目太多，无法猜），拿到后：
  `Application.onCreate` 里调 `AutomationShizuku.addStandaloneShizukuPackage("包名")` 即可。
  另可选：跟 `isManagerMergedIntoHost()` 联动，让说明文字别再提示"去下载独立 Shizuku 软件"。
- 验证：`./gradlew --offline :accessibility:compileDebugKotlin :app:compileDebugKotlin`
  → **BUILD SUCCESSFUL in 4s**，0 error / 0 新增 warning。

## 新增 `clickMultipleByDesc` —— 无 id 无 text、只有 contentDescription 的兜底（2026-10-16）
- `AccessibilityServiceExt.kt` 新增 `suspend fun AccessibilityService?.clickMultipleByDesc(desc,
  startIndex = 0, count = 1, gestureClick = true)` —— **与 `clickMultipleByIdAndText` 同款**：
  suspend、`startIndex`/`count` 切片、逐项 `copyNodeCompat → 点击 → recycleCompat`、每项 `delay(500)`、
  返回**最后一轮**结果（不是「全部成功」）。与 id/text 版的唯一区别 = 定位依据换成 `contentDescription`
  （`default()` 归一化后精确相等，与 `it.text.default() == text` 对称）；**不看 text**。
- ⚠ **第一版被否**：我最初写成非 suspend 单点版（`clickByDesc(desc, gestureClick, mode, index)`，
  自带 `MatchMode` 匹配 + `index` 消歧 + clickable 祖先提升），用户要求「风格和
  `suspend fun clickMultipleByIdAndText` 保持一致」→ 已按那个函数逐行复刻重写。教训：给这个文件加同族
  函数，先照抄既有那一个的结构，不要自创 `mode` / `index` 这类「更好用」的参数形状。
- 配套 private `AccessibilityNodeInfo.findNodesByDesc(desc)`：系统**没有**「按 desc 找节点」的 API
  （只有 byId / byText），自己前序遍历收集**全部**命中节点（树序）；子树整体无命中时把 child 就地
  `recycleCompat`（防全树扫描节点堆积），缓存 `childCount`。命中节点由调用方回收。
- `clickMultipleByDesc` 多做了一步既有 id/text 版**没有**的清理：`drop/take` 切片**之外**的节点立即归还
  （既有版直接丢弃未被切片的节点 → 泄漏）。此差异已在代码里注释，属有意为之。
- **纯提取**：`findNodeByTextOrDesc` 内的局部 `match(value)` 提为 top-level private
  `matchKeyword(value, keyword, mode)`（`MatchMode` 四个模式全库唯一实现），旧函数改为调用它，行为等价。
- 点击语义沿用同族 `gestureClick(node) || node.click()`。⚠ `gestureClick`（扩展函数）恒返回 true
  ⇒ 默认分支等价于**纯手势点击**；`gestureClick = false` 才是 ACTION_CLICK 优先、失败补手势。
- 验证：`./gradlew --offline :accessibility:compileDebugKotlin :app:compileDebugKotlin`
  → **BUILD SUCCESSFUL in 27s**，只剩既有两条 `Unnecessary safe call`（`:1048` / `:1073`，
  属 `findLast { it.text?.default() == ... }` 既有代码，非本次引入）。

## `checkSelectToSpeak` 增加异步版（2026-10-16）
- 用户诉求：`AccIsOpenUtil.checkSelectToSpeak(time)`（他已在库里写好）不该由宿主自己包线程。
- 新增 `checkSelectToSpeakAsync(time: Long = 1500L, onResult: ((Boolean) -> Unit)? = null)`
  （`@JvmStatic @JvmOverloads`）：内部跑同步版，结果经 `Handler(Looper.getMainLooper()).post`
  **回主线程**回调；**同步版保留不动**（零破坏，宿主现有调用点不受影响），只补了 KDoc
  （它原来没有函数级 KDoc，现写明「**阻塞**、含 `SystemClock.sleep`、别在 UI 线程调」）。
- 线程实现：`AccIsOpenUtil` 内私有 `checkWorker` = `Executors.newSingleThreadExecutor` + daemon 线程
  `xpq-check-sts`。**刻意不借 `AppExecutors`**：① 那个是共享**单线程**池，本任务最长 sleep 1.5s 会把
  同池的其它任务堵住；② 独立单线程天然让重复调用**串行**（独占开启是整表替换，并发写会互相覆盖）。
- 形状先例：`XpqAcc.connectUiAutomation` 的 KDoc 已写明「连接是阻塞操作 → 内部后台线程执行，
  onLog / onResult 切回主线程，宿主可放心在主线程调用」，本次照抄该形状（它是裸 `Thread{}.start()`，
  这里换成单线程池）。
- **子线程安全性已逐项核实**：`LogWrapper_NoNet.logAppend_NoNet` / `sendLog`（写文件）、
  `XpqAcc.mode`（`driver` 是 `@Volatile`）、`onlyWhiteAccessibilityIsEnabled`（settings + AMS binder）、
  `XpqAcc.enableAccessibilityServiceOnly`（shell / settings 写，本就应该在子线程）、`SystemClock.sleep`
  都无主线程假设；`AliveUtils.toast` 内部是 `ContextCompat.getMainExecutor(context).execute{}` **自带切主线程**
  ⇒ 整段放进子线程是安全的。
- 遗留（已告知用户，等他定）：同步版里 `val result = XpqAcc.enableAccessibilityServiceOnly(...)` 的
  **返回值未被使用** —— 开启**直接失败**时（既无 shell 也无 `WRITE_SECURE_SETTINGS`）仍要白等满
  `time` 毫秒才回读判 false；可改成「失败即回 false、不 sleep」，能省掉这段无谓等待。
- 验证：`./gradlew --offline :accessibility:compileDebugKotlin :app:compileDebugKotlin`
