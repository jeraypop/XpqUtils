## UiAutomation 连接报 InvocationTargetException（异常未解包）
现象：开启 UiAutomation 模式经常报笼统的 `InvocationTargetException`，看不到真实原因。
根因：system_server 拒绝注册（如 already registered）时，异常被层层包裹：真实异常 → `handleConnect` 包成 `RuntimeException`（ProxyUiAutomationConnection:192）→ `UiAutomation.connect` 的反射 `invoke` 再包成 `InvocationTargetException`（InvisibleAutomation:209）。而 `connect` 的 catch 只取 `e.javaClass.simpleName`（="InvocationTargetException"），没解包。
修复：`InvisibleAutomation.connect` 的 catch 里递归解包（while root.cause != null 且 root 是 InvocationTargetException/RuntimeException，guard<10），`lastError` 显示最内层真实异常（如 IllegalStateException: already registered）。
- 待真机确认：解包后若显示 `already registered`，说明 system_server 残留旧注册（connect 前 disconnect 清理不彻底或进程重启后残留），需进一步加"already registered 时清理重试"或重启 Shizuku。

## 解包 bug：过度解包 RuntimeException 导致看到 "remote stack trace"
现象：上一版解包后，报错变成 `remote exception / remote stack trace`，仍看不到真实原因。
根因：AOSP `Parcel.readException` 里，客户端读回的异常 = `createException(code,msg)`（如 IllegalStateException("already registered")）+ `cause = RemoteException("Remote stack trace:\n"+远程堆栈)`（Parcel.java:3018-3028）。而我的解包条件 `root is RuntimeException` 太宽泛——`IllegalStateException`/`SecurityException` 都继承 RuntimeException，导致解包循环把真实异常继续解包，一路解到 cause 链里的 `RemoteException("Remote stack trace")`，反而丢失真实原因。
修复：解包条件改为**只解包 `InvocationTargetException`**（反射 invoke 的壳），不解包 RuntimeException。解包后 root = handleConnect 抛的 `RuntimeException("registerUiTestAutomationService 失败: already registered")`，message 已含真实原因。
关键规律：**解包反射异常时，只解 InvocationTargetException，绝不解 RuntimeException**（RuntimeException 是所有业务异常如 IllegalStateException/SecurityException 的父类，解它会把真实异常跳过、掉进 Binder 的 RemoteException("Remote stack trace") cause 链）。
- 构建 `BUILD SUCCESSFUL`。

## already registered：残留注册 + 重试
现象（真机确认）：`IllegalStateException: UiAutomationService ... already registered!`，切换模式时"经常"报。
根因：system_server 的 UiAutomationManager 只允许一个 UiAutomation 注册。connect 前 disconnect 清理（`ua.disconnect()`）是异步的，紧接着 connect 就撞上还没注销完的旧注册；或 connect 失败后 mUiAutomation=null 无法用新 client 注销旧注册，导致持续残留。
修复：`InvisibleAutomation.connect` 重构为 `connectRetry(context, timeoutMs, onLog, attempt)`；catch 里解包后若 `root.message` 含 "already registered"，则 `cleanup() + SystemClock.sleep(500) + connectRetry(attempt+1)` 重试一次（attempt<1 限制），等旧 client binder 被 GC、system_server 自动注销后重连。
- 若重试一次仍失败（残留更顽固），需重启 Shizuku 或重启手机。
- 补充：重试一次仍 `already registered` 时（App 进程被杀、旧 client binder 拿不到，app 内清理不掉），`lastError` 改为 `"UiAutomationService 残留注册无法自动清理，请重启 Shizuku（或重启手机）后重试"`，经 onResult reason 传回宿主提示。
- 构建 `BUILD SUCCESSFUL`。

## bind() 复用 bug：disconnect 误杀 UserService 进程导致二次绑定超时
现象：「绑定成功后再次绑定」报 `bind()返回null：绑定超时或被拒绝`。
根因：`connectUiAutomation` 每次连接前无条件 `disconnect()`，而 `InvisibleAutomation.cleanup()` 里 `mSvc?.let { AutomationShizuku.unbind() }` 用 `removeTask=true` 杀掉了 Shizuku UserService 进程并把 `userService` 置 null；下次 `bind()` 走全新绑定需重新 fork 进程，易超时返回 null。

关键规律：**Shizuku UserService（shell exec 通道）是可复用的，disconnect UiAutomation 时不应解绑它**；解绑会导致重连需重启进程、易超时。UiAutomation 的 already registered 清理靠 `ua.disconnect()` + `handleDisconnect()`，与 UserService 无关。
- `AutomationShizuku.unbind()` 现无调用点（保留作未来彻底释放用）。

## 事件桥接 ANR（关键坑）
现象：自动事件桥接成功后，软件无响应（ANR）。
根因：`setOnAccessibilityEventListener` 回调发生在 UiAutomation 线程（InvisibleAutoThread），桥接后 `handler.onAccessibilityEvent` → `dealEvent` 在此线程**同步**执行重活——`TYPE_WINDOW_STATE_CHANGED` 分支里 `XpqAcc.rootInActiveWindow()`（跨进程 binder，慢）+ `copyNodeCompat()`（遍历整棵树）。UiAutomation 事件高频时连续触发，阻塞回调线程 → 主线程业务的 UiAutomation 同步接口（clickByText/getRoot）变慢 → 主线程 ANR。无障碍模式不 ANR 是因为 rootInActiveWindow 是本地缓存快。
修复：`bridgeAccessibilityEvent` 里事件回调改为 `AppExecutors.executors4.execute { runCatching { handler.onAccessibilityEvent(event) } }`，异步化到后台单线程池，保持事件顺序且不阻塞 UiAutomation 回调线程（重活与系统回调解耦）。
关键规律：**UiAutomation 事件回调线程（InvisibleAutoThread）上绝不能同步执行重活**（跨进程 getRoot / 遍历节点树），必须异步提交到线程池。
- 构建坑：编译偶发 `shrunk-classpath-snapshot.bin 拒绝访问` + `Daemon compilation failed` → 大量 Unresolved reference 级联误报；`./gradlew --stop` 后重试即可（非代码问题）。

## 关键规则（无缝切换架构核心）
库内所有「接收 AccessibilityService 参数」的点击/手势方法，其 service 参数最终都只是**判空摆设**——真正执行点已收敛到 `HumanTouchEngine.click`（走 XpqAcc 门面 + fallbackScope）和 `XpqAcc.dispatchGesture`（走门面），节点操作（getBoundsInScreen/performAction）跨通道通用。
因此：这类方法的 `service == null` 判空应**去掉**（执行点完全不依赖 service 时，如 xpqclickNode/moniClick），或**改成 `service ?: accessibilityService` 兜底**（后续还用 service 取 root 时，如 unlock 三函数/moveAwait），否则宿主显式传 null/instance 时在 UiAutomation 模式下会误判。保留 service 参数仅作 API 兼容。
⚠️ 另一类隐患：**lateinit 字段只在无障碍服务 onServiceConnected 里初始化**（如 AssistsWindowManager.windowManager），UiAutomation 模式不拉起服务 → 未初始化 → 访问即 UninitializedPropertyAccessException。凡 UiAutomation 模式代码路径会访问的、依赖无障碍服务生命周期初始化的 lateinit/单例，都必须改成可空 + 兜底（`instance ?: appContext` 或通道感知）。
