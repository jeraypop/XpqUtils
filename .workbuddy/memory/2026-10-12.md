## 定位崩溃：SecurityException(enabled_input_methods) —— 输入法保活按钮
- 用户给了一张 `exception.txt` 截图（release 包，Nubia NX729J / Android 15）：

- 关键代码位置：`accessibility/.../inputmethod/KeepAliveInputMethod.kt:246`（炸点）、
  `:293` `isDefaultIme()`（读 DEFAULT_INPUT_METHOD，**确认安全，不用改**）、

- 已给用户可直接套用的补丁（改用 `InputMethodManager.getEnabledInputMethodList()` 比对

## 回答「不论怎么启动，双活时以无障碍优先」（只读排查，用户明确要求先不动代码）
- 可行性：**能做，但有两个必须先解决的前提**。
- 前提①：**`use()` 会互踢，双活根本建立不起来**——`use(UIAUTOMATION)` 会
  `SelectToSpeakServiceAbstract.instance?.disableSelf()`，而 `connectUiAutomation()` 第一行就是
  `use(UIAUTOMATION)`。所以走官方入口连 UiAutomation 必然把无障碍服务关掉 → 双活永不成立 →
  优先级规则没有适用场景。必须同时让「连 UiAutomation 不顺带关无障碍」（或把 `use()` 降级为「只记意图」）。
- 前提②：**判据判不出「服务在但点了没效果」**。`A11yDriver.isConnected` = `accessibilityService != null`
  （即 `accessibilityServiceLiveData.value`），只能回答「服务是否被系统绑着」。用户的原始痛点恰是
  「服务开着、点击无效」→ 只做优先级会把问题页**永久锁死在无效的 a11y 上**。故优先级之上还需
  **运行期降级**（动作返回 false 时这一轮改用另一通道重试 / 连续失败翻转优先并加冷却）。
- 改动清单（若做「派生 driver」形态）：`XpqAcc.kt:87` `var driver` → 计算属性 + `resolveDriver()`；
  `use()`(134-164) 去掉互踢、改为记意图；`connectUiAutomation()` 第一行(242)；`currentService()`(452)
  要与 `driver.mode` 保持一致；`SelectToSpeakServiceAbstract.onServiceConnected/onUnbind/onDestroy`
  (190/292/322) 触发重算；`InvisibleAutomation.connect/disconnect` 处触发重算。
- **最容易漏的一条**：`driver.mode` 从 UIAUTOMATION 变回 ACCESSIBILITY_SERVICE 时，之前
  `autoBridgeAccessibilityEvent` 建的桥接会与系统回调**重复**（事件跑两遍 → `asyncHandle_XXX` 执行两次），
  必须在 resolve 变化时调 `teardownUiAutomationBridge()`（`XpqAcc.kt:79`）。
- 会自动跟随 `driver` 的业务判断（须回归验证）：`AliveActivity.kt:126-139, 474-482`、
  `AliveUtils.kt:1348, 1496-1498`、`JieSuoUtils.kt:62`、`XpqAcc.kt:91 mode` / `:94 isConnected`。

## 回答「connectUiAutomation(enableHostAccessibilityService = true) 后能否拿到真实无障碍实例」
- 结论：**分入口**。`XpqAcc.currentService()` ❌（按 mode 分支，UIAUTOMATION → proxyService）；
  `SelectToSpeakServiceAbstract.instance` ✅ 与顶层 `accessibilityService` getter ✅ **能拿到**，
  但要等系统重新绑定（`onResult(true)` 时大概率还是 null）；`XpqAcc.driver` 仍是 uiDriver。
- 机制：enable 走 `hostAccessibilityServiceFlat()`（反射宿主清单里带 `BIND_ACCESSIBILITY_SERVICE` 的服务）
  + `AccessibilityEnableHelper` 写系统名单 → 系统再 `bindService` → `onServiceConnected()` → `instance = this`。
- 前提三条（缺一条就永远 null，且只有一行 log）：宿主 manifest 声明了该服务；shell 或
  WRITE_SECURE_SETTINGS 至少一条可用；注意 `use(UIAUTOMATION)` 会先 `instance?.disableSelf()`
  把服务关掉，所以是「先关再开」。
- **发现一处守卫不对称（值得记住）**：`SelectToSpeakServiceAbstract.onServiceConnected()` 第 190 行
  **无条件** `accessibilityServiceLiveData.value = this`；而 `onUnbind()`(292) / `onDestroy()`(322)
  清空时有 `if (XpqAcc.mode != EngineMode.UIAUTOMATION)` 守卫。
  → 于是开了 `enableHostAccessibilityService` 后：`driver`=uiDriver（`XpqAcc.*` 走 UiAutomation），
  但 `accessibilityService`=**真实实例**（`accessibilityService?.xxx()` 走真实无障碍），
  且 `A11yDriver.isConnected` 也变 true（它只看 `accessibilityService != null`）。
  即「两条通道同时被业务代码用」，走哪条取决于调用方写的是 `XpqAcc.*` 还是 `accessibilityService?.xxx()`。
- 想等实例就绪：挂 `SelectToSpeakServiceAbstract.listeners`（companion 里的 public
  `CopyOnWriteArrayList<AssistsServiceListener>`，`onServiceConnected` 会遍历回调），
  或观察 `accessibilityServiceLiveData`。

## 回答「双开时点击改走 UiAutomation」（只读排查，用户明确要求先不动代码）
- 需求：有些目标页在**纯无障碍模式**下节点点击(ACTION_CLICK)与手势点击(dispatchGesture)都无效，
  希望「无障碍为主 + UiAutomation 挂后台」时点击改走 UiAutomation。
- 关键结论（三条点击链路的路由方式不同，决定了可行性）：
  1. **节点点击**（`AccessibilityNodeActionExt.click(gesure=false)` / 各处 `performAction(ACTION_CLICK)`）
     路由**由节点来源决定**，不由 driver 决定（节点自带 connectionId，动作沿该 connection 回 system_server）。
     → 想走 UiAutomation 必须用 `InvisibleAutomation.getRoot()` 的节点（或按 viewId 在 UiAutomation 树里重定位）。
     所以「节点点击换通道」不能靠改 driver 实现。
  2. **手势点击**（`click(gesure=true)` → `GestureExt.gestureClick` → `HumanTouchEngine.click`
     → `XpqAcc.dispatchGesture`）路由**由单槽 driver 决定** → 可改。
  3. **坐标点击**（直接 `HumanTouchEngine.click(x,y)` / `InvisibleAutomation.tap`）同理可由门面决定。
- 前提缺口：**目前没有「两个都连上但 driver 仍是 a11y」的入口**。`use()` 互踢
  （切 UiAutomation 时 `SelectToSpeakServiceAbstract.instance?.disableSelf()`，同进程 instance 非空 → 真的关），
  且 `connectUiAutomation` 第一行就是 `use(UIAUTOMATION)`。既有「双开」姿势其实等于
  **driver=UiAutomation（全部能力走 UiAutomation）+ 无障碍只收事件**，与用户想要的正相反。
  绕法：直接 `UiAutomationDriver.connect()`（= `InvisibleAutomation.connect`）不动 driver，
  且它**不做事件桥接**（桥接只写在 connectUiAutomation 里）→ 正好避免事件双跑。
- 性能代价（会影响决策）：UiAutomation 点击 = shell 进程（单次 fork 50~150ms，`tapNew` 一次点击 fork 3~5 次）。
  **纠正上一轮的错误结论**：`InvisibleAutomation.kt:656` 的 `SystemClock.sleep(1000L)` **其实还在**
  （注释写着「已移除」但代码没删，位于 `dispatchGesture` 的滑动分支）→ UiAutomation 每次滑动固定多等 1s。
- 推荐落点：手势可配「优先 UiAutomation」（改 `XpqAcc.dispatchGesture`/`performGlobalAction` 路由
  + 新增不切 driver 的连接入口）；节点点击不做换路由，改为**失败降级到坐标点击**（走 UiAutomation）。
- 排查动过的文件：`AccDriver.kt`、`A11yDriver.kt`、`UiAutomationDriver.kt`、`XpqAcc.kt`(use/connectUiAutomation/
  dispatchGesture/performGlobalAction)、`GestureExt.kt`、`AccessibilityNodeActionExt.kt`、
  `HumanTouchEngine.kt`(dispatchAsync/performGestureInternal/activeScope)、`InvisibleAutomation.kt`(tap/dispatchGesture)。

## 已落地：`currentService()` 改为「真实实例优先，与通道无关」（同日）
- 用户把上一轮的大方案收窄为一条：**只要两者同时存在，`currentService()` 永远返回真实无障碍服务；
  点击仍走 UiAutomation**。于是只改返回值选择，完全不动 `driver`。
- 改动（`XpqAcc.kt` `currentService()`）：
  `when (driver.mode) { A11Y -> instance; UIAUTOMATION -> proxyService }`
  → **`SelectToSpeakServiceAbstract.instance ?: proxyService.also { it.ensureAppContext() }`**；
  同步更新该方法的 KDoc + `autoBridgeAccessibilityEvent` 里 "service 传 proxyService" 的注释。
- 副作用（必须记住）：**这只改"返回哪个实例"，不改点击通道**。手势仍由 `driver`(=uiDriver) 决定；
  但拿到真实实例后直接调 `service.dispatchGesture / performGlobalAction / getRootInActiveWindow`
  走的是**真实无障碍实现（即 a11y）**。改动前这些调用打在 proxyService 上会失败（mConnection null），
  改动后会成功但走 a11y。→ 纪律：**取根与点击统一走 `XpqAcc.*` 门面**，`currentService()` 只用于
  需要真实 `AccessibilityService` 对象（context / serviceInfo / 事件分发）的场景。
- 附带好处：与 `accessibilityService`（liveData，`onServiceConnected` 会覆盖成真实实例）口径一致了，
  少一处「两个入口答案不同」的不一致。
- 影响面：`currentService()` 共 5 个调用点 —— `SelectToSpeakServiceAbstract` 4 处 `eventData.service`、
  `XpqAcc.kt:509` `onUiAutomationReady(currentService())`；全部变为「真实优先」。
- 前提仍在：要有真实实例，无障碍服务必须真被系统绑着。走 `connectUiAutomation()`（不带
  `enableHostAccessibilityService`）时 `use()` 会先 `disableSelf()` → `instance` 为 null → 仍返回
  proxyService。`./gradlew :accessibility:compileDebugKotlin --offline --no-daemon` → BUILD SUCCESSFUL in 24s。

## 模式弹窗「无障碍模式 + 确定」：有 WRITE_SECURE_SETTINGS 就代码直开（2026-10-12）
- 需求：`showEngineModeDialog` 选无障碍模式点确定时，先查 `WRITE_SECURE_SETTINGS`；有 → 直接代码开启无障碍，
  不弹跳转设置的引导；没有 → 保持原逻辑（切模式 + `showCheckDialog(... BTN_ACCESSIBILITY)` 跳设置）。
- 实现在 `XpqAcc.showEngineModeDialog` 的 `setPositiveButton`：抽出局部 `handleModeResult` 与
  `applyModeAndGuideToSetting()`（= 原逻辑整段，含 onConfirm + showCheckDialog），再按
  `canEnableAccByCode` 分流。原 onResult lambda 只是搬进 `handleModeResult`，行为未变。
- 代码开启路径（后台线程）：
  1. `hostAccessibilityServiceFlat()` 取宿主无障碍组件名 → `AccessibilityEnableHelper.enableAccessibilityService(ctx, flat)`
     （内部先试 Shizuku shell、再走 WRITE_SECURE_SETTINGS；本场景通常 shell 不可用 → 走后者）。
  2. 成功后**轮询等 `SelectToSpeakServiceAbstract.instance` 就绪（最多 3s，100ms 步进）**——
     因为系统 `bindService` 是异步的，不等就会让 `applyEngineMode` 的 `instance != null` 判定误报失败。
     **用户定案：超时也算失败**（不是"再等等"）→ 走 `applyModeAndGuideToSetting(failToast = ...)`
     退回跳转设置的引导。判定式：`ready = result?.success == true && instance != null`。
     时限/步进用局部 val `readyTimeoutMs = 3_000L` / `readyPollStepMs = 100L`（`const val` 不能定义在函数内）。
  3. 回主线程调 `applyEngineMode(...)`；成功走原 toast（**不弹跳转引导**，因为 secure 表已写入成功）。
  4. 失败（无组件 / 写入回读失败 / 绑定超时）→ `applyModeAndGuideToSetting(failToast=具体原因)`：
     它用 `failToast` 顶掉 onResult 里的通用失败提示，然后照旧弹引导对话框。
- **线程模型（用户问「会阻塞主线程吗」后核对）**：不在主线程阻塞。写 secure 表 + 回读 + 最多 3s 轮询
  全在 `Thread{}.start()` 里；主线程只做 `applyEngineMode`（无障碍分支= `saveEngineMode` + `useAccessibilityService`
  + 一次 `instance != null` 判定）、`onConfirm`、`showCheckDialog`。唯一的重活是 `use()` 从 UIAUTOMATION 切回
  ACCESSIBILITY_SERVICE 时的 `teardownUiAutomationBridge()` + `InvisibleAutomation.cleanup()`
  （反射 `ua.disconnect()` 一次 binder + `mProxyHelper.handleDisconnect()` + `mHandlerThread.quit()`，
  **不 unbind UserService**）→ 几 ms ~ 几十 ms，无 ANR 风险，但确实在主线（这是原有行为，非本次引入）。
- **行为差异（宿主需知道）**：代码开启路径下 **`onConfirm` / `onResult` 不再同步**——要等后台线程走完
  写表 + 绑定等待（最长 3s）才在主线程回调；而走引导路径时 `onConfirm` 仍是立即回调。弹窗本身在点「确定」时
  就已消失，用户会先看到弹窗关闭、最多 3s 后才出现 toast。
- 注意：`Activity.checkSelfPermission` 判的就是本 App 的授权状态；该权限来源是 `connectUiAutomation` 连接后
  默认执行的 `pm grant` 那条 `WRITE_SECURE` 命令（uid 2000 执行合法），所以「用过 Shizuku 模式」的机器上再选
  无障碍模式就会命中直开分支。
